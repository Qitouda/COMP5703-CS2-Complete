# 前后端联调实施方案

目标：先让浏览器真正请求后端、可靠展示任务状态和报告，再让同一条链路处理真实论文。沿用已有页面、字段合同与后端 /v1 接口，不重写 UI，不把示例报告当成论文分析成功。

依据：本地 frontend 1250c7a、backend 59fcf3e；实际实现前若有新提交，先重新核对差异。本文为待实施工作方案，未修改业务代码。

## 1. 两个验收阶段

| 阶段 | 可测试内容 | 退出标准 |
|---|---|---|
| A：真实接口联调 | 浏览器→HTTP 后端→示例评估→真实状态查询→页面 | 浏览器不读取 mock 报告；选项、上传、创建、查询、错误均经过后端；能展示报告与证据，清楚标注示例评估 |
| B：真实论文测试 | 相同前端→真实上传或 arXiv 获取→解析→真实模型→校验→报告 | arXiv、PDF 各一例成功；结果与实际论文相符；失败和不确定性准确；保存版本与运行证据 |

A 可先做，不需要等待模型调优和全部人工样本；B 是“产品可以真实测试”的必要条件。A 完成只能关闭接口联通问题，不能直接关闭 BE-02/BE-06 或完整 MVP 验收。

## 2. 统一接口，采用后端现有路径

| 前端动作 | 请求 | 前端处理 |
|---|---|---|
| 读取评估标准 | GET /v1/venues | 只允许选择可用项 |
| 读取模型 | GET /v1/models | 只允许选择可用项；没有可用模型时阻止提交并提示 |
| 提交 PDF | POST /v1/uploads，multipart 字段 file | 取得 upload_id 与文件名，再创建任务 |
| 创建分析 | POST /v1/assessments，JSON | 取得创建回执中的 assessment_id，随后查询完整快照 |
| 读取进度/结果 | GET /v1/assessments/{id} | queued/processing 继续查，completed/failed 停止 |
| 重试可重试任务 | 先 GET 原任务确认 retryable，再 POST /v1/assessments | 用原 source/venue_id/model_id 创建新任务；保留旧记录，不需要先新增 retry 端点 |

前端 getOptions() 可并行调用两个选项端点并组装 {venues, models}，不用让后端额外做 /api/options。

arXiv 创建请求示例：

```json
{
  "schema_version": "0.4",
  "source": {
    "type": "arxiv",
    "arxiv_id": "2307.08122v3",
    "original_url": "https://arxiv.org/abs/2307.08122v3",
    "upload_id": null,
    "original_filename": null
  },
  "venue_id": "iclr_2027_main",
  "model_id": "model_fixture_v1"
}
```

model_id 只是阶段 A 示例，实际使用选项接口返回的用户选择值。PDF 请求保持同一结构，source.type=pdf，填写上传响应的 upload_id、original_filename，arxiv_id/original_url=null。浏览器上传 FormData 不手动设置 multipart Content-Type，以免丢失 boundary。

## 3. 后端先补的接口条件

负责人：孙海晨；具体执行人由组内确定。

1. **所有查询响应补全 Assessment。** 创建时就保存 source、venue 快照、model 快照、warnings=[]、error=null、paper=null、report=null、started_at/completed_at=null。成功和失败沿用同一形状。GET 使用 Assessment 响应校验，不能只校验 report 子对象。创建接口保留轻量回执是允许的，前端不可直接把它当完整任务。
2. **上传必须收到真实文件。** 读取内容、检查空文件/类型/大小、私有保存、建立 upload_id→路径/元数据映射。缺失或过期 ID 返回可理解错误；不把私有路径发给浏览器。阶段 A 也要测试真实上传，示例评估可以暂不读取正文。
3. **校验选项和输入。** venue/model 必须存在且可用；arXiv 规范化和格式校验；PDF Source 互斥字段检查；用户选择的 model_id 必须路由到对应配置，不能忽略选择。
4. **稳定错误形状。** 建议 HTTP 错误统一 {code,message,debug_id}；状态快照中的业务失败继续使用 error 对象。若保留 FastAPI detail 包裹，前端适配层统一展开，不能要求每个组件自行兼容。
5. **交付启动说明与测试响应。** 一个启动命令或明确步骤、监听地址，以及 queued/processing/completed/failed 示例。测试场景使用固定可控 provider/测试夹具，不依赖模型随机制造失败，不向普通用户开放无保护的故障注入接口。

先以单实例服务和私有上传存储跑通开发测试。内存任务会在重启后丢失，需要前端正确处理 404；要做共享长期测试时再交持久化或明确任务保留方案。无需为了启动联调先补齐 Celery。

## 4. 前端工作包

总负责人：曾博成；实现支持：傅饶、吴冬乔。

| 文件/模块 | 改动 |
|---|---|
| 新增 src/api/httpAssessmentApi.ts | 实现 getOptions/createAssessment/getAssessment/retryAssessment；封装 HTTP 错误、请求超时和响应基础校验 |
| src/api/assessmentApi.ts | 将创建回执与完整任务的边界写清。建议 createAssessment 返回创建回执，hook 根据 ID 查询；mock 实现同步遵守新接口 |
| src/types/assessment.ts | 分离 VenueRef/ModelRef 与带可用性等字段的 Option；快照使用 Ref；按后端合同对 error/warning 的可空字段对齐，禁止靠类型断言掩盖缺字段 |
| src/App.tsx | 使用统一 api 实例；通过显式环境配置选择 mock/http；HTTP 模式不回退 mock，不展示 mock 场景选择 |
| src/hooks/useAssessment.ts | 分开保存任务 ID 与快照；创建成功后立即查一次；查询失败继续可控重试，显示连接问题；卸载/换任务取消旧请求，避免旧结果覆盖新任务 |
| InputWorkspace.tsx | 根据真实选项设置默认值和可用性；校验 PDF 基本类型/空文件，后端做权威校验；避免重复提交 |
| AssessmentReport.tsx | 适配完整响应；增加 claimed_contributions；缺必需字段时显示响应错误，不能自行补假论文、模型或报告 |
| AssessmentProgress/错误提示 | 处理中也显示查询失败、重新查询入口；仅 error.retryable=true 提供重试；明确重试会创建新任务 |
| vite.config.ts / 环境示例 / README | 开发时同源请求 /v1，代理到本机后端；为共享测试环境配置同源反向代理；记录运行模式与启动步骤 |

建议开发默认 http，mock 仅显式启用时使用。例：VITE_API_MODE=http，前端 5173，后端 8000，开发代理 /v1→http://127.0.0.1:8000。部署产物不能依赖 Vite 开发代理，需要部署侧路由 /v1 到后端。模型密钥只在后端配置。

建议轮询间隔 2 秒；临时网络/5xx 错误退避至 4/8 秒，连续三次后保留任务 ID 并显示“暂时无法查询，可继续查询”。停止浏览器轮询不代表后台任务失败。创建/上传请求不自动重发，避免网络响应丢失导致重复任务或重复付费；只有幂等机制建立后再支持自动重发。真实后台任务超时由后端设置并返回明确错误。

## 5. 接通真实论文的工作包

负责人：孙海晨；赵龙翔提供数据与 rubric。

1. 将 upload_id 解析为实际 PDF 路径；arXiv 获取精确版本的 PDF，并保留来源/版本/哈希。
2. 接入可运行解析器。可先复用数据组 pypdf 试点并通用化，不强制等待 GROBID；必须去除写死来源及自动“人工通过”，提取或合并标题、摘要、章节、页码和正文。
3. 保留现有 ParsedDocument/source_index 适配，真实解析结果进入原有编排与证据校验。
4. 把评分指南、版本和完整报告结构要求加入 Prompt；真实模型可用性经最小调用验证；模型选择与实际调用一致。
5. 修复不可靠证据仍保留高置信度评分的问题；不能用“JSON 合法”作为“判断可靠”的证明。
6. 保存 input/version、assessment_id、实际模型、Prompt/rubric 版本、耗时/token、最终结果与失败记录。

可先用 paper_001 已有解析产物跑一次后端内部模型测试，快速验证 Prompt/字段；这只是中间检查点，不代表浏览器上传已经解析成功。

## 6. 联调验收清单

| 场景 | 通过条件 | 阶段 |
|---|---|---|
| 启动与选项 | 选项来自网络接口，后端停机时明确提示而非显示 mock | A |
| arXiv 创建 | 网络中提交正确 source；取得后端 ID，查到完整快照 | A |
| PDF 上传 | file 请求带真实字节；后端私有保存；任务使用返回的 upload_id | A |
| 示例报告 | 页面展示后端返回报告与证据，明确示例模式 | A |
| 处理中与业务失败 | 页面读后端状态；重试只对可重试错误开放 | A |
| 网络故障 | 暂时断开后端连接可见提示，恢复查询后显示原任务结果 | A |
| 非法输入 | 空/伪 PDF、非法 ID、无效模型、不存在 upload_id 不返回成功分析 | A/B |
| 真实 arXiv | 实际论文标题、内容、证据对应输入，真实模型运行记录可查 | B |
| 真实 PDF | 本地上传文件与解析哈希一致；报告基于该文件；不是固定 7.2 分模板 | B |
| 不确定与不可解析 | 缺少证据使用 null/uncertain；不可解析返回结构化失败，不伪造报告 | B |
| 相同论文两入口 | 版本/哈希一致时解析内容一致；模型评分可有波动，不要求完全相同 | B |

每条记录至少包含：日期、三仓库提交号、运行模式、输入版本/哈希、assessment_id、预期、实际、通过/失败、截图或响应文件。结果结构测试应覆盖完整 Assessment；增加浏览器联调测试，不只调用后端 TestClient。

## 7. 推荐执行节奏与移交

- 第一个工作日：后端修完整响应、输入/上传、错误；前端并行写 HTTP 适配层与轮询恢复。当天目标是阶段 A 中 arXiv/PDF 均经真实接口得到明确标注的示例报告。
- 第二个工作日起：后端接真实解析和模型，数据组提供版本明确的样本和 rubric；前端继续做故障场景与字段验证。阶段 B 需按实际模型权限和解析问题估时，不能仅承诺“改 URL 就完成”。
- 阶段 A 验收由前后端共同演示；阶段 B 加数据组逐条核查证据，曾博成签收。

对下一轮的具体承诺应写为：**先交可复现的 HTTP 联调版本，再交至少一篇真实 arXiv 和一份真实 PDF 的页面测试记录。** 这样前端可以立刻开工，真实分析的未完成工作也有清晰责任和验收边界。
