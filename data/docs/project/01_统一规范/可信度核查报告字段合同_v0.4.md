# 可信度核查报告字段合同 v0.4

版本：`credibility-0.4.0-draft`，2026-10-19，本地实现合同。沿用 [v0.3](可信度核查报告字段合同_v0.3.md) 的全部公开字段、引用核实率和原因结构，本次澄清代码外部证据的有界计划完成语义及关联后续查行为。合同仍是草稿，真实技术运行与正式人工／跨组验收分别记录。

## 1. 版本与评分兼容

接口不变：`POST /v1/credibility/assessments`、`GET /v1/credibility/assessments/{id}`。新调用省略 `schema_version` 时使用 `credibility-0.4.0-draft`。显式 0.1／0.2／0.3 请求继续被接受并保留各自原有序列化结构；v0.4 和 v0.3 公开字段形状相同，仓库、讨论、引用、来源及核实率字段不新增枚举。旧报告不迁移、不重新检索。

| 请求版本 | 公开报告结构 |
|---|---|
| `credibility-0.1.0-draft` | 原 0.1 结构；无 coverage／execution／external_review／reference_verification_summary |
| `credibility-0.2.0-draft` | 原 0.2 结构；无 reference_verification_summary |
| `credibility-0.3.0-draft` | 原 0.3 结构，含引用摘要 |
| `credibility-0.4.0-draft`（默认） | 与 0.3 相同字段；使用下述代码证据流程及完成语义 |

`rubric_version` 独立于传输版本。当前 `0.2-provisional-complete` 的文件字节、条目映射、权重、阈值与公式不改。模型仍不输出评分，也不能设置 `scoring_eligible` 或独立复现身份。相同固定 checks 在四版传输下产生同样逐项、分项和总分；引用核实率的分母和未核实原因遵从 v0.3。

## 2. 有界代码检查计划与范围

`dimensions[code_reproduction].check_status`、对应 `execution.checks.code_check.status` 表示声明的有界采集／核查计划是否完成。`checks.code.scope_complete`、`scope_limitations` 和 coverage 单独表示论文附属材料及全网搜索范围是否完整，不能混用。

- 有界计划已执行完、无尚未恢复的技术失败或待执行步骤时可为 `completed`，即使全网／讨论总量未知，`scope_complete=false` 仍须保留。
- 因请求／模型轮数预算耗尽、无法读取预定材料、缺少必要页或未完成语义核查时为 `partial`；意外失败并不能形成有效分项时为 `failed`。
- 完成有界计划且没有找到明确官方仓库，只能报告限定范围未找到／关联不确定，不能声称论文未开源或研究无法复现。
- 有分数、模型调用完成、讨论列表请求返回成功，都不能单独使范围完整或待执行步骤完成。

执行检查点保留显式 partial，不误存为 completed。内部恢复可重试未完成分支，并复用已经核验的基础来源和其他已完成分支；GET 仅读快照。历史数据维持原状态，本合同不把旧失败记录改成成功。

## 3. 语义确认仓库后的后续采集

执行顺序为基础有界代码检查 → 必要的模型语义核查 → 对本轮新确认的仓库读取真实实现入口及讨论 → 若新增讨论仍需语义判断，再执行至多一次有界语义补查。

后续采集使用已确认的仓库、实际 revision／子目录和来源关联证明；不能因仓库从 uncertain 改为 confirmed 就假称实现与讨论已读取。只有关联和材料足够时才更新代码可用性；空列表、失败访问与范围不足分别保留。已有成功采集与来源不重复覆盖。

语义输出经过引文／权限校验并保存有效输出快照后，即使另一次工具读取失败使该阶段为 partial，仍可保留有证据的仓库确认并继续确定性采集；该失败与最终 partial 必须保留，后续成功不能覆盖。没有有效输出快照的 partial，以及 failed／unsupported，不触发基于新确认的后续采集。

基础采集、模型工具和确认后的采集共享每次执行最多 40 次来源读取操作（`LOOKUP.get`／工具读取，包含缓存命中），模型实际轮次受配置总上限约束，第二语义阶段只使用剩余来源读取和轮数预算。实际网络 HTTP 另行审计，包含传输层有界重定向产生的额外跳转；40 次来源读取不是 40 次网络 HTTP 的上限。预算不足时保留已取得材料和具体停止原因，不另开一套预算绕过限制。

## 4. 来源、审计与内部状态

公开 `external_review` 沿用既有 `mode / status / audit_ref / warnings / base_facts_reused` 字段。`audit_ref` 可以指向合并审计快照，内部关联全部语义阶段的输入、工具执行、输出和失败尝试；后续阶段不能覆盖前一阶段轨迹。`report.versions.model_calls` 保留实际记录的所有模型调用。供应商隐含推理、密钥和本机文件内容不公开。

已确认仓库后续采集的完成记录、请求数和恢复状态保存在内部 CodeCheckResult／阶段快照中，不添加到公开 checks／repository 字段。原 source／evidence／finding 链路仍须闭合，模型新引用须来自实际读取且符合当前目标权限的原文。

## 5. 验收与前端消费

前端可以继续消费 v0.3 的字段形状，升级默认版本时将“有界计划已完成”和“范围未穷尽”分别展示；不以 scope_complete=false 单独展示为服务故障。真实模型验证需保留新任务的论文／代码／模型／Prompt／Rubric 版本及完整工具证据，模拟测试不替代真实调用。

验收覆盖四版真实 POST／GET JSON 形状、同固定 checks 评分一致、预算 partial 检查点恢复、模型新确认仓库后的真实内容／讨论读取、必要第二语义阶段的共享预算和全部审计保留。本文只登记合同，不预写真实多论文通过结果。
