# 可信度核查报告字段合同 v0.5

版本：`credibility-0.5.0-draft`，2026-10-19。本合同先于实现登记自动外部代码发现的结果与证据语义，沿用 [v0.4](可信度核查报告字段合同_v0.4.md) 的有界执行、确认后补查、全部审计及原评分规则。实际运行结果另行记录，本合同不预写通过数。

## 1. 版本与兼容

接口仍为 `POST /v1/credibility/assessments`、`GET /v1/credibility/assessments/{id}`。省略 `schema_version` 时默认 `credibility-0.5.0-draft`；显式 0.1–0.4 请求继续接受，按原版本投影，不增加 `code_discovery`。旧报告和阶段快照读取时可在内部补默认 `not_run`，不发起新检索，不迁移或覆盖历史结论。

| 请求版本 | 公开报告结构 |
|---|---|
| `credibility-0.1.0-draft` | 原 0.1；无 coverage／execution／external_review／reference_verification_summary／code_discovery |
| `credibility-0.2.0-draft` | 原 0.2；无 reference_verification_summary／code_discovery |
| `credibility-0.3.0-draft` | 原 0.3，含引用摘要；无 code_discovery |
| `credibility-0.4.0-draft` | 原 0.4，与 0.3 字段相同；无 code_discovery |
| `credibility-0.5.0-draft`（默认） | 在 0.4 上新增报告顶层 `code_discovery` |

原 `checks.code`、repository、discussion、source 的字段和枚举保持不变。新增发现结果单独报告，不把搜索命中塞成已确认官方仓库。

## 2. 新增 `report.code_discovery`

内部 `CodeCheckResult.discovery` 使用同一类型并有默认工厂，以兼容旧检查点。默认状态 `not_run`、空查询／候选、零预算使用量和明确未执行原因；不是“已经搜索但未找到”。

| 字段 | 类型／语义 |
|---|---|
| `status` | `not_run / disabled / not_needed / completed / partial / failed` |
| `reason` | 本次状态或停止原因，不能用技术失败推断没有公开代码 |
| `scope_complete` | 固定 `false`；有界发现不能证明全网穷尽 |
| `queries` | 下述查询记录列表 |
| `candidates` | 下述候选资源列表 |
| `budget` | 下述已配置上限与真实使用量 |
| `limitations` | 未搜索、未读取、超限、截断、权限、分页或身份不确定等具体缺口 |
| `audit_ref` | 可空；不可变发现审计快照，关联模型尝试、工具、查询、页面读取与登记过程 |

`completed` 仅表示声明的有界发现计划已完成。结果为空仍不证明无代码；查询错误、必要正文不可读或预算中止必须分别记录 `partial / failed` 及原因。有已有充分官方代码证据而跳过时可为 `not_needed`；关闭配置用 `disabled`，没有运行用 `not_run`。

### 2.1 查询记录

`{query_id, provider, query, status, result_count, source_ids, reason}`：

- `query_id` 为本次发现过程内唯一 ID；`provider` 为非空供应商／检索渠道名称，`query` 是实际执行或计划的查询文字。
- `status` 为 `completed / partial / failed / not_run`。成功空结果与失败严格分开：成功返回零命中可 `completed, result_count=0`；限流、超时、格式错误、访问失败不能据此宣称无代码。
- `result_count` 是本次实际登记的有界命中数，不是供应商声称的全站总量；非负整数。
- `source_ids` 关联报告实际来源。检索响应使用既有 `source.kind=metadata`，保存请求、供应商、查询及原始／规范化响应快照；未运行的查询可无来源。

### 2.2 候选资源

`{candidate_id, url, title, resource_kind, status, repository_id, query_ids, source_ids, evidence_ids, reason}`：

- `candidate_id` 为本次发现内唯一 ID；`url` 是真实发现的目标 URL；`title` 可空。
- `resource_kind` 为 `implementation_candidate / official_implementation / third_party_reproduction / third_party_related / reading_list / undetermined`。
- `status` 为 `candidate / verified / rejected`。搜索命中或初步页面判断只能 `candidate` 或 `rejected`；不因标题、摘要或搜索排名直接确认。
- 初始未定资源使用 `undetermined`；无明确官方声明的疑似实现用 `implementation_candidate`。实际读取的页面同时包含本论文身份和明确官方实现声明时，可以登记 `official_implementation`，但状态仍为 `candidate`；只有既有 checker／语义判断依据实际 README 等原文确认仓库后，才能标记为 `verified`，并带实际 `repository_id`、来源及证据 ID。确认后的实现内容／讨论仍须实际读取，不能由发现状态替代。
- `third_party_reproduction` 指明确针对本论文的第三方复现实现，须与只使用本论文做相关比较／基准的 `third_party_related` 分开；`reading_list` 只是文献／资源列表。它们不自动成为官方仓库，不自动触发官方代码分数或可评分的独立复现身份。
- `repository_id` 可空；非空时必须指向报告 `checks.code.repositories` 的实际记录。`query_ids` 仅指向本摘要查询，`source_ids / evidence_ids` 仅指向报告实际来源／证据，全部 ID 必须闭合。
- 搜索摘要可证明“发现了这个候选”，不能单独证明官方归属、实现可用、本文复现或评分。归属依据必须来自实际读取的原文，保持搜索响应 → 目标页面 → 仓库 immutable revision／README → 论文身份的证据链。

### 2.3 预算

`budget` 中均为非负整数，默认零：

- `max_queries / queries_used`
- `max_candidates / candidates_inspected`
- `max_source_reads / source_reads_used`
- `max_model_rounds / model_rounds_used`
- `max_tool_calls / tool_calls_used`

本摘要 budget 只记录 discovery 阶段自身的配置上限与真实使用量。失败模型尝试和工具调用也计预算；查询和正文读取的 provider 操作一并计入来源读取，缓存命中也计操作。搜索、基础采集、语义工具、确认后采集共享每次执行最多 40 次来源读取。发现阶段显式配置最多 4 个模型轮次／8 次工具调用；既有仓库／讨论语义核查跨其两个阶段合计最多 3 个模型轮次／6 次工具调用。两阶段分别受固定上限约束，组合最多 7 轮／14 次工具，不能相互借用或自动扩容；组合实际总数由外部审计汇总。网络 HTTP（含受控重定向）独立审计，不等同于来源操作数。预算中止保留实际已执行与未执行项目。

## 3. 自动闭环与权限

执行自动有界发现时，可依据当前论文准确标题、明确 arXiv ID 与作者生成查询，归档实际检索响应；读取候选正文并登记来源后，才把真实公开仓库候选交给原有 checker。登记不能让搜索来源获得官方归属引文权限。原有 native tools 的已发现 registry 按实际来源扩充，不允许模型任意创建 URL、凭据或仓库关联。

候选进入 checker 后保持原关联规则：确认需原文和论文身份兼容；第三方基准、阅读列表和仅引用本文的资源分别解释，不把“提到论文”当作官方实现。确认后复用 v0.4 的实现／讨论真实补查和必要第二语义阶段，并保留所有阶段输入、原始输出、修复、失败尝试及来源快照。失败搜索不覆盖已经取得的正面官方代码证据。

通用网页搜索与 GitHub 搜索是不同渠道。GitHub Token 仅为 GitHub 认证凭据，不提供通用网页搜索。缺少检索渠道、限流、权限失败、正文无法读取、截断及 ID 绑定不足都必须显式报告，不能以模型记忆代替实际查证。

## 4. 评分与验收

`0.2-provisional-complete` rubric 文件字节、阈值、类别、权重和计算保持不变。发现摘要不直接评分；有新的有效材料时只通过既有 checks 评分。同一固定 checks 在五个传输版本下，逐项分、分项分和总分一致。未审核讨论继续 `scoring_eligible=false`，不把搜索数量／命中数乘入可信度分数。

验收包含五版真实 POST／GET 投影、默认 0.5、旧快照无网络读取、来源与候选 ID 闭合、官方候选不得只靠搜索摘要变 verified、搜索空结果与技术失败分开、预算共享及全部审计保存。真实论文实跑须用新原文解析、真实供应商与来源快照；原历史失败和重试记录保持独立，不能用模拟测试或组合结果冒充一次全通过。
