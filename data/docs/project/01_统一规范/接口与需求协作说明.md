# 接口与需求协作说明

旧五维评分继续使用字段合同 v0.4；第二轮新增 **Paper Credibility Check** 已有独立报告合同 v0.1 评审稿。数据、后端、前端三组对同一份新合同确认评分、来源、时间、未核实、不适用和失败语义后联调。本轮任务编号与范围见[R2C 清单](../03_过程与交付/第二轮_交付任务清单.md)；下文旧评分差异交接内容只作历史参考。

2026-09-22 已补齐[可信度报告字段合同 v0.1](可信度核查报告字段合同_v0.1.md)与[可信度 Rubric v0.1](../03_过程与交付/数据样本与%20Rubric/可信度核查_Rubric_v0.1.md)评审稿。可据此开展实现讨论和标注清楚的试验，尚未代表正式字段冻结、规则批准或接口开发完成。

## 数据组交给后端的内容

本轮每条可信度建议至少写清：问题编号、论文版本、检查维度、实际结果、独立人工判断、论文／外部证据与核查时间、期望行为、适用性、优先级和验证样本。旧五维问题若影响保留功能，仍可按原差异记录法提交。可能涉及 Rubric、Prompt、正文上下文、解析、外部接口、输出校验或模型配置；原因未确认时标为假设。

后端补充实现方法、影响范围、所需时间和变更版本，产品组确认优先级。模型评分偏高不直接等于应统一减分，需先说明具体判断或规则的问题。

## 前端交给后端的内容

| 交接项 | 必须说清楚的内容 |
|---|---|
| 用户需求 | 谁在什么场景下使用，当前哪里不方便 |
| 操作流程 | 入口、步骤、目标页面及返回路径 |
| 数据要求 | 页面展示哪些字段，哪些可缺失，数据从哪里来 |
| 状态要求 | 加载、成功、空结果、失败及恢复行为 |
| 接口要求 | 是已有接口可满足，还是需要新增或修改；提供请求与响应示例 |
| 范围和依赖 | 必做与可选部分、后端依赖、预估工作量和排期影响 |
| 验收 | 可重复的操作步骤、预期结果和对应任务编号 |

前端给出需求方案，后端确认技术可行性并补全接口约定；双方确认后再安排开发联调。最终接口名称和字段由双方记录，不能只依赖聊天口头约定。

## 合同与历史结果兼容

- 旧五维报告继续沿用 [统一字段合同 v0.4](旧五维评分字段合同_v0.4.md)；新可信度报告须有单独版本，不能复用旧分数语义。
- 涉及字段、枚举、评分或空值语义变化时，列出变更点及新旧版本的读取方式，经产品、数据及相关开发组确认后更新合同。
- 报告记录实际论文、模型、Prompt、Rubric 和解析版本；缺失的历史信息明确标注未知，不用当前配置补写成历史事实。
- 数据分析表可以增加内部评测字段；这些字段不自动成为对外接口或页面功能。
- 失败或无法评估不能伪装成成功报告，也不能用 Mock 内容替代真实失败。

## 任务状态

使用“待确认、待开始、进行中、待联调、待验收、已完成、阻塞、延期”。进入开发前填执行人、预期结果和日期；标记完成时附验证证据。阻塞项记录依赖人、缺少的输入及下一步。

数据任务另行记录效果结论：“未试验、改善、无明显改善、变差、证据不足”。不要把“文档交付完成”和“模型效果改善”写进同一个状态。
