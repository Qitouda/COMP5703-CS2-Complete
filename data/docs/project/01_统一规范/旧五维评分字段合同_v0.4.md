## 1. 第一轮已锁定的旧评分定义（历史功能）

> 本项目参考 CSPaper，构建一个带评分和论文内证据定位的尽职调查工具。系统接收 ArXiv 链接或 PDF，从研究价值、证据充分性、原创性、清晰度和可复现透明度等维度评估论文，并帮助读者判断是否值得进一步阅读、引用或使用；MVP 不运行代码复现实验。

### 1.1 MVP 必须支持

- ArXiv 链接或 ArXiv ID。
- PDF 上传。
- Venue 选择界面；MVP 只提供 ICLR 一个选项，交互可参考 CSPaper。
- 模型选择界面；MVP 只提供少量经后端确认可用的模型。
- 五个固定维度的 1–10 分评分。
- Overall Score、总体等级和阅读建议。
- Strengths、Concerns、Unresolved Questions。
- 可复现透明度 checklist。
- 每个重要判断绑定论文内证据。
- 处理状态、警告和明确错误。
- 模型名称、模型版本和分析时间，用于结果追溯。

### 1.2 MVP 明确不做

- 实际运行代码或复现实验。
- ICLR Accept/Reject 或录用概率预测。
- 跨论文 Review Ranking。
- 自动推荐优先阅读章节。
- 明确判断论文是否“可以安全引用或使用”；该能力进入后续版本。
- 完整 GitHub 健康度检查。
- 撤稿数据库、PubPeer 和全网社区信号聚合。
- 独立的 SOTA 专项评分、榜单检索或全球最新 SOTA 验证；论文中的 SOTA 声称按普通主要 claim 检查。
- 公开分享链接；PDF 和报告默认私有。

## 2. 字段设计原则

1. **一个含义只有一个字段。** 不同时出现 `status`、`state`、`result_status` 表示同一件事。
2. **任务状态与分析结论分开。** `failed` 是任务状态；`uncertain` 是评估结论。
3. **缺失、无法判断和不适用分开。** 不使用 `0` 或空字符串混合表达。
4. **重要判断必须可追溯。** 有评分或重要结论，就必须有 `evidence_links`，并说明每条证据与该判断的关系；没有可靠证据时必须降低置信度或返回 `uncertain`。
5. **前端不自行计算业务结果。** Overall Score、等级和阅读建议由后端返回；前端只展示。
6. **前端不写死 venue 和模型目录。** 可选项由后端配置接口返回。
7. **原始文件默认私有。** 不在公开字段中返回可长期访问的原始 PDF URL。
8. **字段可版本化。** 所有结果必须包含 `schema_version` 和 `rubric_version`。

## 3. 命名与空值规则

| 类型 | 规则 | 示例 |
|---|---|---|
| 普通字段 | 英文 `snake_case` | `overall_score` |
| ID | 以 `_id` 结尾 | `assessment_id` |
| 时间 | 以 `_at` 结尾，ISO 8601 UTC | `completed_at` |
| 布尔值 | 以 `is_`、`has_`、`can_` 开头 | `is_provisional` |
| 数组 | 使用复数名 | `authors`, `evidence_links` |
| 枚举 | 小写 `snake_case` | `not_applicable` |
| 无法获得 | `null`，并给出原因 | `score: null` |
| 已知为空 | 空数组 `[]` | `authors: []` |
| 禁止 | 用空字符串表示缺失 | `title: ""` |

通用 `confidence` 枚举：

```text
high
medium
low
```

- `high`：论文信息清楚，判断有直接且可靠的证据支持。
- `medium`：有相关证据，但仍存在有限信息缺口或解释空间。
- `low`：证据较弱、解析不完整或判断高度依赖推断。

前端、后端和数据处理不得为不同对象分别创建第二套置信度枚举。

## 5. 输入 Source 字段

### 5.1 ArXiv 输入

```json
{
  "type": "arxiv",
  "arxiv_id": "2501.01234",
  "original_url": "https://arxiv.org/abs/2501.01234",
  "upload_id": null,
  "original_filename": null
}
```

### 5.2 PDF 输入

```json
{
  "type": "pdf",
  "arxiv_id": null,
  "original_url": null,
  "upload_id": "upl_01",
  "original_filename": "paper.pdf"
}
```

### 5.3 约束

- `type` 只能是 `arxiv` 或 `pdf`。
- `arxiv` 输入必须提供 `arxiv_id`；`upload_id` 必须为 `null`。
- `pdf` 输入必须提供 `upload_id`；`arxiv_id` 可以在解析后补充。
- API 不接受同时提交 ArXiv 和 PDF 作为同一任务的两个主来源。
- 文件大小、页数和 MIME type 上限由后端确认，确认后应加入接口文档，不改变本对象业务含义。

## 9. 任务状态和处理阶段

### 9.1 `status`

| 值 | 用户文案 | 含义 |
|---|---|---|
| `queued` | 等待开始 | 已创建任务，尚未处理 |
| `processing` | 正在分析 | 任一处理阶段正在执行 |
| `completed` | 分析完成 | 报告已完成并通过基本结构校验 |
| `failed` | 分析失败 | 无法返回可靠完整结果 |

### 9.2 `stage`

```text
validating_input
retrieving_paper
parsing_paper
analyzing
linking_evidence
finalizing_report
report_ready
```

### 9.3 规则

- `status` 表示任务生命周期；`stage` 表示处理位置。
- `completed` 必须对应 `stage: report_ready` 和 `progress_percent: 100`。
- `failed` 时保留失败发生时的 `stage`。
- `uncertain` 和 `not_applicable` 不得作为任务 `status`。
- 进度百分比是用户体验信息，不作为分析完成度或质量分数。

## 10. 评分体系

### 10.1 固定维度

| `dimension_id` | 展示名称 | 核心问题 | v0.1 权重 |
|---|---|---|---:|
| `research_value` | Research Value & Significance | 工作是否提供值得继续阅读或使用的新知识与价值？ | 0.20 |
| `soundness_evidence` | Soundness & Evidence Support | 方法、理论或实验是否支持主要 claim？ | 0.20 |
| `originality_positioning` | Originality & Positioning | 贡献是否清楚，与既有工作的关系是否合理说明？ | 0.20 |
| `clarity_usability` | Clarity & Usability | 问题、方法、实验和结论是否容易理解与使用？ | 0.20 |
| `reproducibility_transparency` | Reproducibility & Transparency | 是否提供足够的复现信息与实验透明度？ | 0.20 |

第一版使用等权重，但保留 `weight` 字段，未来经产品决策可以调整。历史报告必须保存实际使用的权重。

### 10.1.1 Rubric 责任与版本治理

- 产品组已经锁定五个维度的名称、字段结构、1–10 分形式、Overall Score 计算方式和 MVP 产品边界。
- 数据处理组负责完善每个维度的具体检查项、评分锚点、证据要求、`uncertain` / `not_applicable` 判断规则、样本选择和人工试评方法。
- 后端组负责把已确认的 rubric 实现为大模型 Prompt、调用流程和结构化输出，并记录实际使用的 `rubric_version`。
- 数据处理组评测不同模型、Prompt 和推理参数的结果，向后端提供调优反馈；后端负责实施和记录技术调整。
- 不改变现有字段、枚举、权重和产品语义的 rubric 细化，通过更新 `rubric_version` 管理，不要求升级 `schema_version`。
- 如果 rubric 调整改变维度含义、字段、枚举、权重或 Overall Score 规则，则必须由产品负责人确认，并按第 26 节升级字段合同版本。

### 10.2 DimensionAssessment

```json
{
  "dimension_id": "soundness_evidence",
  "display_name": "Soundness & Evidence Support",
  "applicability": "applicable",
  "score": 8,
  "rating": "good",
  "weight": 0.2,
  "summary": "主要实验支持核心结论，但部分比较缺少消融。",
  "confidence": "medium",
  "uncertainty_reason": null,
  "evidence_links": [
    {
      "evidence_id": "ev_03",
      "stance": "supports",
      "reason": "The reported main results support the assessment of the paper's core claim."
    },
    {
      "evidence_id": "ev_07",
      "stance": "context",
      "reason": "The ablation description provides context for the remaining limitation."
    }
  ]
}
```

`DimensionAssessment.applicability` 只能是：

```text
applicable
uncertain
not_applicable
```

字段组合必须满足：

- `applicable`：`score` 为 1–10，`rating` 按分数映射，`uncertainty_reason` 为 `null`。
- `uncertain`：`score` 为 `null`，`rating` 为 `uncertain`，`uncertainty_reason` 必须为非空说明。
- `not_applicable`：`score` 为 `null`，`rating` 为 `not_applicable`，`summary` 必须说明不适用原因，`uncertainty_reason` 为 `null`。

### 10.3 分数与等级映射

| 分数 | `rating` | 展示含义 |
|---:|---|---|
| 9–10 | `strong` | 很强，证据充分 |
| 7–8 | `good` | 较好，存在有限问题 |
| 5–6 | `adequate` | 基本达到要求，但有明显局限 |
| 1–4 | `weak` | 关键方面较弱或证据不足 |
| `null` | `uncertain` | 无法可靠判断 |
| `null` | `not_applicable` | 不适用于该论文 |

### 10.4 空值与计算规则

- 分数只能是整数 1–10 或 `null`。
- 禁止用 `0` 表示无法判断、缺失或不适用。
- `uncertain` 与 `not_applicable` 不参加 Overall Score 计算。
- 少于三个维度有有效分数时，`overall_score` 必须为 `null`，总体等级为 `unable_to_assess`。
- 任一维度为 `uncertain` 或 `not_applicable` 时，`is_provisional` 必须为 `true`。
- 每个有数字分数的维度至少绑定一条可靠证据。
- 前端不得根据维度分数重新计算总体分，以后端返回结果为准。

### 10.5 Overall Score

第一版使用已评估维度的归一化加权平均：

```text
overall_score = Σ(score × weight) / Σ(参与计算的 weight)
```

返回一位小数。示例：`7.6`。

```json
      "reason": "The experimental setup indicates that some baseline conditions may not be directly comparable."
    }
  ]
}
```

`support_level`：

```text
supported
partially_supported
unsupported
uncertain
```

SOTA 不使用独立字段或专项模块。若论文作者明确或隐含声称达到 SOTA、最佳已报告结果或同类最高性能，该声称作为普通 `ClaimCheck` 返回：

- `claim` 记录作者具体提出的声称，不把系统推断写成作者原话。
- `support_level` 只表示论文内部证据对该声称的支持程度。
- `reasoning` 说明任务、数据集、指标、主要 baseline、比较条件和统计信息中实际能够核查的部分。
- `evidence_links` 至少连接声称出现的位置及其结果依据；两者位于同一处时可以引用同一 Evidence。
- MVP 不通过外部榜单检索验证该结果是否为全球真实、最新的 SOTA。
- SOTA 声称不单独加分，也不直接决定 Overall Score。

## 15. Evidence 字段

### 15.1 EvidenceReference：证据内容与位置

```json
{
  "evidence_id": "ev_06",
  "page_number": 7,
  "section_id": "sec_04",
  "section_title": "4.2 Main Results",
  "locator_type": "table",
  "locator_label": "Table 2",
  "evidence_mode": "quote",
  "excerpt": "Our method improves accuracy by...",
  "location_confidence": "high"
}
```

`EvidenceReference` 只描述证据是什么以及证据位于论文哪里，不包含 `stance`。同一条证据可能支持一个判断、反对另一个判断，因此关系必须记录在使用该证据的具体判断中。

### 15.2 EvidenceLink：判断与证据的关系

```json
{
  "evidence_id": "ev_06",
  "stance": "supports",
  "reason": "Table 2 reports higher accuracy than the listed baselines."
}
```

| 字段 | 类型 | 必填 | 可空 | 业务含义 |
|---|---|---:|---:|---|
| `evidence_id` | string | 是 | 否 | 指向同一报告 `evidence` 数组中的证据 |
| `stance` | enum | 是 | 否 | 该证据与当前具体判断之间的关系 |
| `reason` | string | 是 | 否 | 为什么该证据支持、反对或仅提供背景 |

### 15.3 枚举

`locator_type`：

```text
text
figure
table
equation
theorem
```

`evidence_mode`：

```text
quote
paraphrase
```

`EvidenceLink.stance`：

```text
supports
contradicts
context
```

- `supports`：证据增加当前判断成立的依据。
- `contradicts`：证据与当前判断相反，或显示当前判断存在例外。
- `context`：证据帮助理解当前判断，但不能直接证明或反驳它。

`location_confidence`：

```text
high
medium
low
```

### 15.4 Evidence 验收规则

- 每个有数字分数的维度至少有一个 `evidence_link`。
- 每个 `major` strength 或 concern 至少有一个 `evidence_link`。
- 每个 `EvidenceLink.evidence_id` 必须能够在同一报告的 `evidence` 数组中找到。
- 每个 `EvidenceLink` 必须填写 `stance` 和非空 `reason`，说明证据与当前判断的具体关系。
- `stance` 不得放在 `EvidenceReference` 中；同一 Evidence 可以被多个判断引用，并在不同判断中使用不同 `stance`。
- 有 Figure、Table、Equation 或 Theorem 编号时填写 `locator_label`；否则可以为 `null`。
- 页码无法可靠确定时，`page_number` 为 `null`，并将 `location_confidence` 设为 `low`。
- `quote` 必须是论文原文短摘录；概述必须标记为 `paraphrase`。
- 找不到可靠证据时不得编造页码、引文或图表编号，应降低置信度或返回 `uncertain`。

| 请求/响应字段 | 组织确认 | 提交与消费 | 定义并实现接口 | 输出统一结果 |
| 状态与错误 | 确认用户语义 | 展示用户文案 | 产生状态和错误码 | 提供数据处理失败类型 |
| Evidence | 确认产品要求 | 按具体判断展示关系、原因和定位 | 校验并传输 EvidenceLink | 抽取证据并建立判断关系 |
| Overall Score | 确认公式和文案 | 不自行计算 | 统一计算/返回 | 提供维度分数 |
| 数据隐私 | 确认产品原则 | 不暴露私有 URL | 实现访问控制和保留策略 | 不外传原文 |

## 21. 前端验收清单

- [ ] ArXiv 和 PDF 两种输入都能提交。
- [ ] Venue 页面显示 ICLR 单一选项，但保留可扩展选择结构。
- [ ] 模型选项来自后端，不写死第二份列表。
- [ ] 正确展示 `queued / processing / completed / failed`。
- [ ] 五个维度都能展示 1–10 分、等级、理由、置信度和证据。
- [ ] `uncertain` 与 `not_applicable` 不显示为 0 分。
- [ ] 每个判断下的 Evidence 能显示 `supports / contradicts / context`、关系原因、页码、章节和适用的图表/公式编号。
- [ ] Overall Score、阅读建议和局限说明位置明确。
- [ ] 不创建独立 SOTA 模块；相关声称只在 `claim_checks` 中按普通 claim 展示。
- [ ] 不显示 Accept/Reject、Review Ranking、推荐章节或引用保证。
- [ ] 失败时显示可理解错误和可重试状态。

## 22. 后端验收清单

- [ ] 请求和响应字段与本文示例一致。
- [ ] 对输入、枚举、分数范围、必填与互斥字段进行校验。
- [ ] Venue 和模型使用稳定 ID，并提供统一选项来源。
- [ ] `deepseek v4Flash` 只有在 API、权限和最小样本调用验证通过后才标记为可用。
- [ ] 备用模型和 API 可用性有明确记录；不可用时不会向前端返回可选状态。
- [ ] 大模型输出经过结构校验、失败重试和证据引用检查。
- [ ] 内部日志能够追踪 model、rubric、Prompt/配置版本和关键推理参数。
- [ ] 状态和阶段不会产生前端未定义的新值。
- [ ] Overall Score 按本文规则计算并返回一位小数。
- [ ] `EvidenceLink.evidence_id` 不存在悬空引用，且每个 link 都有合法 `stance` 和非空 `reason`。
- [ ] 错误不暴露堆栈、密钥、服务器路径或私有文件 URL。
- [ ] 历史报告保留 schema、rubric 和 model 版本。

## 23. 数据处理验收清单

- [ ] 主动建立 3–5 篇公开论文的初始样本集，并记录选择理由与测试用途。
- [ ] 五个维度均有具体检查项、评分锚点、证据要求和无法判断规则。
- [ ] 两名成员使用同一 rubric 完成人工试评并记录评分分歧。
- [ ] 对后端不同模型、Prompt 或参数结果形成可追踪的效果反馈。
- [ ] 始终返回五个维度对象，即使某项为 `uncertain` 或 `not_applicable`。
- [ ] 有数字评分的维度至少包含一个可靠 `evidence_link`。
- [ ] Major strength/concern 至少包含一个可靠 `evidence_link`。
- [ ] Evidence 本身不输出 `stance`；关系仅记录在具体判断的 `evidence_links` 中。
- [ ] Quote 与 paraphrase 不混淆。
- [ ] 找不到页码或证据时不编造。
- [ ] 可复现 checklist 使用固定六项和统一状态。
- [ ] 不把缺少代码直接等同于论文低价值。
- [ ] 作者提出 SOTA 声称时按普通 `ClaimCheck` 返回；没有此类声称时不生成占位对象。
- [ ] 不把论文作者的 SOTA 声称表述为系统已完成的外部事实验证。
- [ ] 不输出 Accept/Reject 或录用概率。
- [ ] 不声称已经运行或复现论文代码。

## 24. 共同联调验收

至少使用以下测试样本完成联调：

1. 一篇有效 ArXiv 论文，完整返回报告。
2. 一份有效 PDF，完整返回报告。
3. 缺少作者或部分元数据的论文，返回 warning 而非直接失败。
4. PDF 无法解析的任务，返回结构化 error。
5. 某维度无法判断的论文，正确返回 `score: null` 和 `uncertain`。
6. 理论论文无代码，正确使用 `not_applicable` 或说明，不自动判低价值。
7. 一篇声称 SOTA 的论文，将该声称作为普通 `ClaimCheck` 返回，不出现独立 SOTA 对象。

共同验收通过的最低条件：前端发送的字段、后端接收/返回的字段、数据处理输出的字段完全一致；不存在同义不同名、空值含义冲突或前端临时计算业务结论的情况。

## 25. 仍需技术组确认但不得改变业务语义的事项

- PDF 最大文件大小和最大页数。
- 上传接口采用 multipart 还是预签名上传。
- 异步任务、轮询、SSE 或 WebSocket 方案。
- Venue 和模型选项接口的具体路径。
- 任务与报告的数据库拆分。
- 原始 PDF 和报告的具体保留时长。
- `deepseek v4Flash` 的具体 API、权限和实际供应商版本。
- 后端备用模型与故障切换方案。
- 进度百分比各阶段的技术映射。
- Evidence 跳转 PDF 的具体前端实现。

这些事项由相应技术组提出推荐方案，产品负责人确认用户影响后执行。

## 26. 变更规则

1. 产品语义、评分规则、枚举或报告结构发生不兼容变化时，必须升级合同版本。
2. 仅增加可选说明字段且不影响旧客户端时，可以做向后兼容的小版本更新。
3. 删除或重命名字段属于破坏性变化，必须同步前端、后端、数据处理和测试。
4. 每次变更记录：原因、提出人、影响模块、迁移方式、确认人和日期。
5. 未写入本文件的群聊决定不视为字段合同变更。
