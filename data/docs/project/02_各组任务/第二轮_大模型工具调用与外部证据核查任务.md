## 2. 交付范围

第一版交付以下能力：

1. 读取论文给出的项目网页、GitHub README、文件目录及少量与问题直接相关的文本源码／配置文件。
2. 读取 Issue 正文、评论和维护者／作者回复，保留时间及上下文。
3. 让模型判断仓库是否对应论文、讨论是否针对本篇、涉及什么实验条件、是否有明确成功／失败报告及后续处理证据。
4. 每项结论关联抓取快照和证据 ID；证据不足时返回未知，并保留覆盖缺口。
5. 支持实际工具调用，并明确记录后端预抓取方式，提供跨论文真实验收记录。
6. 任务及分项结果持久化、失败项可恢复，三项检查独立执行并使用受限并发。
7. 分别呈现核查发现、覆盖率、未知项和技术失败；现有试验分与这些解释同时保留。

整体采用“固定工作流调度 → 证据保存 → 模型按需判断／补查 → 程序校验 → 规则计分”。首版范围为第 6 节的 `R2C-BE-07-01～06`；`07-07` 为后续评分校准，不阻塞首版交付。

当前 v0.5 在缺少可确认实现时，可由受控 Search／Fetch 从登记的论文身份查询补充候选；搜索命中仍需实际正文及原检查器确认，不假定已完成全网搜索。登录网页、JavaScript 浏览器渲染、GitLab／Bitbucket 适配及 GitHub Discussions 仍为后续扩展。此任务不安装仓库依赖、不运行论文代码，也不承诺自动复现实验。

## 3. 功能如何操作

### 3.1 使用者操作

使用者继续提交 arXiv 或上传 PDF，选择真实模型并发起可信度核查；不需要手动组织工具参数。沿用已有接口：

```http
POST /v1/credibility/assessments
Content-Type: application/json

{
  "schema_version": "credibility-0.5.0-draft",
  "analysis_mode": "credibility",
  "source": {
    "type": "arxiv",
    "arxiv_id": "2106.09685v2",
    "upload_id": null
  },
  "model_id": "model_gpt_v1",
  "rubric_version": "0.2-provisional-complete"
}
```

通过 `GET /v1/credibility/assessments/{assessment_id}` 查询结果。当前默认使用 [v0.5 合同](../01_统一规范/可信度核查报告字段合同_v0.5.md)，包含覆盖／执行、引用核实摘要与 `code_discovery`；显式 0.1–0.4 请求继续按各自合同返回原形状。实现和真实验收状态见主清单，本地运行不表示已经上线。

### 3.2 后端执行流程

1. 持久化任务身份和版本配置；解析论文并保存产物，固定论文身份、代码声明、候选仓库和项目页位置。
2. 解析完成后，主张、引用和代码三个分支按配置受限并行，各自保存状态和结果；外部请求仍按服务限速。代码分支先读取第一批项目页、仓库和讨论；缺少可确认实现时执行有界发现，将来源绑定的候选交回原检查器，保存带来源 ID 的内容快照。
3. 把论文身份、原文证据和外部内容交给模型。仅在关联不清、关键讨论冲突或关键结论缺证据时补查；模型说明缺口并提出工具请求，后端校验后执行。
4. 把工具结果回传模型，直至模型给出结构化判断，或触发轮数、请求数、时间／内容预算限制。
5. 校验引用、证据原文与判断字段，组装现有 `checks.code / evidence / sources / findings`。
6. 汇总各分支的已验证结果，后端确定性计分；分别给出发现、覆盖、未知和失败原因，保留 `is_provisional`。重试复用已持久化的有效产物，仅重新执行失败或缺失步骤。

### 3.3 已实现且必须区分的两种运行方式

| 方式 | 执行过程 | 必须记录的事实 |
|---|---|---|
| `native_tools`（已实现） | 模型提出工具调用 → 后端执行 → 回传工具结果 → 模型继续判断 | 实际工具名、参数、调用 ID、结果及后续模型调用 |
| `prefetch`（已实现） | 后端按既定流程抓取 → 模型阅读这些内容并判断 | 这是外部证据模型分析，不是模型主动调用工具 |

当前 OpenAI Responses 与兼容 Chat Completions 适配器接入统一工具接口；`native_tools` 与 `prefetch` 由部署配置显式选择，不在任务中自动切换。代码检索使用 OpenAI 搜索与受控网页读取；Claude／Gemini 使用同一检索入口。具体模型协议和完整报告是否通过，仍分别按能力探测与 06 验收记录。

开发接入或模型配置变更时，使用现有 `.env` 中所选模型的配置显式执行最小能力探测并留档，可与 P0 的任务／证据存储设计并行，验证工具协议、当前模型与思考模式是否兼容；不在每次服务启动时自动调用模型。能力不支持时须明确记录原因；可显式采用 `prefetch` 继续语义核查，但不能把它记作原生工具调用验收通过。模型超时、无效输出或达到预算时，保留抓取与失败记录，未完成的判断保持未知。

## 4. 工具与调用循环如何实现

### 4.1 已实现的只读工具与原设计差异

以下是既有仓库／讨论语义工具，注册在 `backend/app/credibility/external_tools.py`；它们只访问已登记候选，不能传入任意新仓库或网页 URL。自动发现阶段另在 `code_discovery.py` 注册 `search_paper_code(query_id)` 与 `fetch_discovery_page(candidate_id)`，参数只能使用本次服务端登记的 ID；新增候选必须经过来源登记与原权限校验。

| 工具 | 主要输入 | 返回内容 |
|---|---|---|
| `read_public_page` | 已登记 `source_id` | 关联项目／补充页的静态正文、来源及抓取状态 |
| `read_repository_readme` | 已登记 `repository_id` | 解码 README 正文及证据来源 |
| `resolve_repository_revision` | 已登记 `repository_id` | 实际默认分支提交 SHA，固定后续文件读取版本 |
| `read_repository_file` | 已登记 `repository_id`、相对 `path` | 固定 SHA 下的有限文本文件与路径；拒绝越界、二进制和凭据类文件 |
| `read_issue` | 已登记 `repository_id`、正整数 `number` | 指定 Issue 标题、正文、公开元数据及来源 |
| `read_issue_comments` | 已登记 `repository_id`、正整数 `number` | 首批最多 30 条评论；有后续内容时明确记录缺口 |

原设计中的 `get_github_repository / list_repository_issues / read_issue_thread` 没有作为当前工具名开放：元数据和列表发现由固定检查器完成，模型通过上述工具读取具体材料。原定能力按实际工具拆分，不能按旧提案名称调用。

统一返回结构至少包括 `status`、`source_id`、最终 URL、获取时间、缓存标记、内容哈希、正文／结构化数据、截断或下一页标记，以及错误原因。网页、文件和评论按可定位片段组织，供模型引用；不只返回一个 URL 或既有规则标签。

### 4.2 调用循环

- 保留已有 `complete_json` 路径，单独增加支持工具的调用接口，避免影响主张核查和旧五维流程。
- 请求中注册固定工具 schema；收到 `tool_calls` 后，按工具名及参数类型校验，再分派到只读执行器。
- 保存模型的工具请求消息；每个调用均以对应 `tool_call_id` 回传结果，包括超时、拒绝或未知工具。多个调用必须逐一对应。
- 模型收到结果后可继续请求或提交最终判断。达到预算后停止补抓，并保留未完成原因；不得无限循环或凭空生成最终证据。
- 对相同参数请求使用已有缓存并识别重复循环；失败重试有明确上限。轮询任务结果不得重新访问网页或模型。
- 工具协议与强制 JSON 输出、思考模式的组合按当前供应商实际协议实测，验证后记录配置；模型必要的协议历史与对外审计日志分开处理，不导出完整推理内容。

抓取限制沿用公开 HTTPS、重定向检查、缓存、限速及单响应大小上限。基础检查最多 4 个仓库、4 个项目页、每仓库 2 页 Issues、每线程 2 页评论；全流程共享 40 次来源读取操作，包含缓存命中，实际网络 HTTP 与重定向另行审计。自动发现最多 4 个模型轮次／8 次工具，仓库及讨论语义跨两个阶段合计最多 3 轮／6 次工具，不相互借用；正文默认 60000 字符、单次最多 16000 输出 token。配置、共享预算及停止条件见后端 `docs/credibility/external-tools.md` 与 `code-discovery.md`，真实验收保存实际配置和停止原因。

外部正文、README、代码注释和评论均作为待分析材料，不能当成系统指令；工具不提供 shell、安装、执行代码或写入仓库能力。继续拒绝私网、带凭据 URL 和越界重定向；本地密钥不进入模型输入或日志。

## 5. 模型判断与报告接入

优先复用已有对象，避免另建一套报告：

| 判断 | 使用现有字段／输出位置 | 验证要求 |
|---|---|---|
| 仓库归属 | `repositories[].association`、关联理由和证据 | 区分本论文实现、基线、同名项目及共享仓库；模型结论不能绕过证据校验 |

### 6.1 R2C-BE-07-01：任务持久化与阶段恢复（P0）

**本地实现依据：** `backend/app/storage/credibility_tasks.py` 新增独立任务／阶段表及带 attempt、token、revision 的租约写入；`app/credibility/runtime.py` 和 `scripts/credibility_tasks.py` 提供查询、显式恢复及重放。`tests/test_credibility_task_storage.py`、`test_credibility_durable_pipeline.py` 覆盖数据库重建读取、原子领取、旧租约拒写、版本指纹及成功检查点复用。

**实现方式：**

- 复用 `app/storage/db.py` 的数据库连接和 Session，参考 `assessment_history.py` 的快照方式，新增可信度专用任务／阶段记录。旧五维 `AssessmentRow` 有 `venue_id` 等约束，不直接套用；提交可兼容现有数据的表结构变更和回退说明。

- 01 与 02 先统一 `assessment_id + stage + attempt + artifact_id` 的关联方式，再分别实现任务记录和证据存储，避免形成相互等待的接口依赖。
- 恢复时校验输入与版本，复用已落盘的有效解析和分项结果，仅重跑失败／缺失步骤。对“请求已发出但响应未保存”的模型尝试标明中断；重试新增尝试记录，不承诺第三方调用恰好一次。
- 首版提供内部恢复命令或管理入口，交付时固定其操作方法。若新增公开重试 API，单独给出合同差异，不在本文虚构已经存在的路径。

**验收标准：**

- [ ] 完成解析及一个分项后停止、重启服务，仍可查询同一任务的持久化状态及已保存产物。
- [ ] 注入中断后恢复，已完成步骤的调用计数不增加；只有失败／未保存步骤产生新尝试，最终结果无重复条目。
- [ ] 输入／版本变化不会误用旧产物；并发或重复恢复不会由两个执行者同时领取同一阶段，旧结果不会覆盖新结果。
- [ ] 模型返回后未成功落盘的窗口有明确状态和重试记录；旧五维历史读取与运行回归通过。

### 6.2 R2C-BE-07-02：证据快照与重放（P0）

**本地实现依据：** `backend/app/credibility/snapshots.py` 实现 SHA256 内容寻址、独立观察记录、原子写入、父链及读取校验；`code_lookup.py / references.py / code_checks.py` 填充来源 `snapshot_ref`，模型输入及审计另行留档。`tests/test_credibility_snapshots.py` 和 `test_credibility_durable_pipeline.py` 覆盖篡改、缺失、失败／截断、缓存、来源身份及无网络／无模型的离线重放。

**实现方式：**

- 保存外部响应中实际读取的内容，补齐现有 `sources[].snapshot_ref`。成功来源记录 URL／最终 URL、时间、内容类型、原始内容哈希、规范化正文及其哈希／处理版本；仓库文件另带 commit、路径和行号，讨论另带线程／评论标识。
- 证据文件可按哈希存放在现有数据目录，数据库保存索引及与任务的关联。先写完整快照再提交引用；中断产生的临时文件可清理，不允许产生指向半写文件的有效证据。
- 把采集事实、模型判断和规则计分分开保存；结论引用已保存的片段，不能只引用实时网页。失败访问保存状态和原因，不伪造正文或有效引文。
- 另存实际进入模型的片段、顺序、截断范围和输入哈希，并关联源快照及模型／Prompt 版本；完整抓取内容和模型实际读到的内容可分别核对。
- 区分两种操作：固定证据重放不联网、不调用模型；基于旧快照重新调用模型必须记录为新分析。使用者要求从头运行时，新建任务并记录实际刷新来源，不把重放标为真实新抓取。

**验收标准：**

- [ ] 原网页变化／不可访问后，仍可从快照回查报告引用；快照哈希一致，行号或评论定位有效。
- [ ] 快照缺失、内容被改动、无效 ID 或引文不匹配时，校验拒收或明确记录无法核实，不输出已验证结论。
- [ ] 固定证据重放的 HTTP 和模型调用次数均为 0；新模型分析和来源刷新各有独立轨迹。
- [ ] 中断写入不会留下有效报告指向不完整证据；缓存命中保留原获取时间，并记录本次使用情况。

## 7. 验收标准

### 7.1 功能与边界测试

完整验收须包含原生工具调用。若当前模型不支持工具协议，`prefetch` 可单独记为“外部证据语义核查通过”；原生工具调用子项保留“能力受限、未通过／待接入”，BE-07 不标记完整完成。

- [ ] 原生模式出现真实 `tool_calls`，后端实际执行并回传对应结果，模型利用结果给出判断；仅有工具名或模拟调用不算通过。
- [ ] 预抓取方式有独立标记；能证明项目页、README、文件内容和讨论正文实际进入模型输入。
- [ ] 覆盖无效参数、未知工具、多工具调用、重复请求、达到上限和无效模型输出；可有界结束。
- [ ] 覆盖 403／404／429、超时、缺页及静态页面无法获取正文；保留失败、截断和未知，不误判为没有代码或没有问题。
- [ ] 覆盖基线仓库误关联、共享仓库、否定／反问、成功失败混合、仅环境问题、关闭但未证明解决等案例。

- [ ] 同一组结构化检查结果仍按现有 0.2 得到相同分数；模型不直接给分、未审查讨论不自动参与计分；旧五维和主张流程回归通过。
- [ ] 任务／证据持久化、重启恢复、分项故障隔离及受限并行按 01～03 验收通过；试验分与覆盖／失败原因按 05 分别解释。

### 7.2 跨论文真实验收

至少选 6 篇真实论文，允许一篇覆盖多种情况，但下面每类都要有实例。样本记录包含版本、人工核对预期、实际结果及证据，不能全用同一个仓库或只展示成功样本。

| 类型 | 核对重点 |
|---|---|
| 独立官方仓库 | 仓库找对；README／文件证据支持关联 |
| 先给项目页再跳仓库 | 项目页的本论文代码链接与基线链接能区分 |
| 多篇论文共用仓库 | 无明确论文依据的帖子不强行归入当前论文 |
