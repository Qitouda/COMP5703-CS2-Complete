# 2026年8月21日客户会议摘要

## 一、Meeting 主要信息

1. 系统需要支持输入 arXiv 链接和上传 PDF。
2. Client 以 CSPaper 作为参考，希望系统帮助用户快速判断论文是否有研究意义、是否值得继续阅读。
3. 代码复现和完整 GitHub 分析比较复杂，不是第一版必须完成的功能。
4. Client 没有明确要求第一版完成撤稿检查、PubPeer 或全网讨论聚合。
5. Client 希望我们形成自己的产品方向，而不是完整复制 CSPaper。

## 二、我的主要发现

### 1. MVP 不应以代码复现为主

第一版更适合做“AI 论文价值初筛”：帮助用户快速理解论文，并判断主要结论是否有证据、研究是否有意义、是否值得进一步精读。

### 2. 建议先采用简化的 ICLR 标准

ICLR 的公开审稿逻辑与 client 描述的目标较接近，可以简化为五个维度：

- Problem and Motivation：研究什么问题，为什么值得研究；
- Soundness and Evidence：方法和实验是否支持主要结论；
- Significance：是否提供有价值的新知识；
- Originality：是否有新方法、新发现或有意义的新组合；
- Clarity：问题、方法和结论是否表达清楚。

### 3. SOTA 是检查信号，不是好坏标签

系统可以检查论文是否声称 SOTA、比较是否合理、提升是否有意义。但“没有 SOTA”不代表论文没有价值，“达到 SOTA”也不代表论文一定可靠。

### 4. 第一版只针对 ICLR 更可行

不同会议和期刊的标准不同。一开始支持全部 venue 会迅速扩大范围。ICLR 标准公开，OpenReview 上也有公开论文和 reviews，比较适合课程项目验证；其他 venue 可以后续扩展。

## 三、建议的 MVP

> 用户输入 arXiv 链接或上传 PDF，系统依据简化的 ICLR 标准，分析论文的研究问题、证据充分性、研究意义、原创性和表达清晰度，生成一份带有主要优缺点、SOTA 分析、证据位置和不确定性的结构化报告。

第一版暂不包含：

- 实际运行代码或复现实验；
- 完整 GitHub 仓库分析；
- 多会议、期刊选择；
- 撤稿、PubPeer 和全网讨论；
- 学术不端判断；
- ICLR 录用概率预测。

## 四、希望团队先确认的三件事

1. 是否同意第一版只针对 ICLR；
2. 是否同意代码复现和外部诚信信号暂不进入 MVP；
3. 是否同意先用公开 ICLR 论文和 reviews 做 prototype 与初步验证。

如有异议，请说明具体风险、替代方案，以及新方案会增加或替换哪些工作，避免重新进行无边界讨论。
