# 第二轮：可信度核查技术难点与提前验证

更新日期：2026-10-01。状态：技术讨论稿，供技术可行性验证和联调使用。

本文的技术讨论起于 9 月 22 日静态检查；10 月 1 日已完成 paper_002 的真实生产 generic PDF 入口来源验证，17／17 检查通过。该结果只验证首例解析与定位，不代表新核查 Agent、外部工具或完整 API 已验收。文中的样本量和验证方法均为建议，不构成已确认的验收承诺。人员分工与排期统一以对应任务文档为准。

关联文档：[产品基线](../../00_项目总览/MVP产品基线.md)、[第二轮开发计划](../../00_项目总览/第二轮_可信度核查开发计划.md)、[交付任务清单](../第二轮_交付任务清单.md)。

## 1. 优先判断

本轮技术难点主要集中在证据获取和判断可靠性。解析时丢失的表格、引用或附录，不能靠更换模型补回；证据位置存在，也不能直接证明它支持模型的结论。

应优先验证以下两件事：

1. **能否准确提取参考文献，并区分匹配成功、存在歧义和查询失败。**
2. **能否为核心主张找到对应证据，并核对实验条件和原文位置。**

| 技术难点 | 可能影响 | 应尽早取得的证据 |
|---|---|---|
| PDF 结构化不足 | 表格、章节、引用被误读，后续判断失去依据 | 多种版式论文的人工对照记录 |
| 主张与证据对照 | 把缺少证据写成矛盾，或比较不同实验条件 | 每条主张及对应证据的人工与系统对照 |
| 引用拆分与匹配 | 真实引用被误判，遗漏被覆盖率掩盖 | 人工总数、提取数、逐条匹配与失败原因 |
| 仓库及讨论归属 | 引用无关仓库，遗漏作者解释和修复 | 论文与仓库关联依据、讨论上下文 |
| 外部依赖与运行时间 | 限流、超时、重试导致整份报告失败 | 请求量、耗时、部分失败及缓存验证 |
| 新报告与评分集成 | 新旧结构冲突，失败项目被排除后产生虚高总评 | 独立合同、状态样例、确定性评分和旧功能回归 |

## 2. PDF 能读出文字，不代表能支撑核查

### 当前已确认的限制

通用解析器主要使用 PyPDF 抽取文字，再用规则识别章节、图表编号和链接。图表记录主要保存编号及附近文字，没有可靠恢复表格单元格、列名和实验条件。generic-pypdf-v2 已改为页内标题分段和跨页章节继承，首例摘要、表 3 及 caption 定位通过；其他版式仍需回归，通用表格单元格和可靠列结构仍未恢复。

项目中的 `GrobidParser` 当前实际调用通用解析器，尚未调用真正的 GROBID 服务。不能因为存在该类或配置项，就认为已经具备 GROBID 的参考文献结构化能力。

依据：[通用解析实现](https://github.com/kanekogaido/cs2-capstone--backend/blob/r2c-sync-2026-10-01/app/parsing/generic.py)、[GROBID 适配实现](https://github.com/kanekogaido/cs2-capstone--backend/blob/r2c-sync-2026-10-01/app/parsing/grobid.py)。

### 具体影响

例如摘要声称“所有数据集均有提升”，反例却只在表格中。如果表格列错位或数值未读出，模型可能找不到反例。参考文献的双栏、换行和跨页也可能造成条目合并或拆散。扫描件目前不应默认视为可支持的输入。

### 提前处理

- 用双栏、复杂表格、长参考文献和带附录的论文检查解析结果，重点比较内容和位置，而非仅检查是否成功返回文本。
- 对读不清的表格、图像或缺失附录记录限制，相关主张允许返回“无法判断”。
- 可试验 GROBID 的引用提取与结构化能力，但先在本组 ML 样本上比较结果，再决定是否接入。
- 初期保留现有解析流程，优先补齐影响三类核查的关键数据，避免同时重写全部解析逻辑。

GROBID 官方支持参考文献提取、解析和文档结构化，但其公开评测结果不能直接当作本项目的效果保证。参考：[GROBID 功能说明](https://grobid.readthedocs.io/en/latest/Introduction/)。

## 3. 主张与证据一致性是判断难度最高的一项

### 难在哪里

摘要写“提高 20%”，实验部分写“提高 12%”，不一定构成冲突。需要确认是否相同数据集、基线、指标、实验设置，以及相对提升还是百分点变化。理论结论、消融结果、限定条件和附录会进一步增加判断难度。

当前已有证据校验可以核对部分引用和位置是否存在，但不足以验证证据在语义上支持结论。现有引文逐字回查是在整篇解析文本中查找；即使找到原句，也不充分证明它位于模型标注的具体段落。

依据：[证据校验实现](https://github.com/kanekogaido/cs2-capstone--backend/blob/r2c-sync-2026-10-01/app/validation/evidence.py)。

### 建议流程

1. 提取摘要和引言中的核心可核查主张，同时保留适用条件。
2. 在方法、实验、结果和附录中寻找对应证据，记录查找范围。
3. 对照数据集、指标、基线、数值单位及条件，再生成判断。
4. 校验引文是否属于所标注的具体文本块，页码是否与该文本块一致。
5. 保存主张与证据两端的位置、判断理由和无法确认的部分。

结果必须区分“找到支持”“部分支持”“未找到对应证据”“找到具体冲突”和“无法判断”。检索遗漏、解析缺失不能直接写成论文内部矛盾。

按 D-041，第一版只提取摘要／引言关键主张，正文、图表和附录用于核对证据。少量条目试跑如实说明范围，遗漏范围内重要主张时 scope_complete=false；复杂公式、图像和必要材料能否支持选定主张通过样例确认，不能可靠读取时保留无法判断。

### 提前验证

先人工确定少量主张及预期证据，再查看系统输出。开发案例应包含：相同条件下的真实冲突、不同条件下看似冲突的结果，以及因材料不足无法判断的情况。记录错误发生在主张提取、证据检索、条件比较还是最终表述。

## 4. 引用核查难在拆分、匹配和消歧

### 难在哪里

真实引用可能没有 DOI，标题存在断行，作者使用缩写，或同时存在预印本与正式发表版本。数据库返回的第一条候选不能自动视为正确匹配；未检索到也不能直接判为虚构。

### 建议拆成三个步骤

| 步骤 | 要保留的信息 | 主要失败状态 |
|---|---|---|
| 提取条目 | 原始引用文本、论文位置、拆分结果 | 无法拆分、字段不完整 |
| 检索候选 | 查询字段、数据源、候选记录、查询时间 | 服务失败、无候选 |
| 判断匹配 | 标识符或标题／作者／年份的匹配依据 | 候选歧义、元数据冲突、未核实 |

优先用明确标识符查询；没有标识符时再做多字段匹配。保留原始条目和候选，便于复查，不用模型凭记忆补全书目信息。

### 覆盖率要防止误导

假设论文实际有 60 条引用，只提取出 40 条，即使这 40 条全部查询完成，也只能说明“已提取条目全部检查”。开发样本应由人工统计总数，以识别提取阶段的遗漏。

真实运行中如果无法可靠确定原始总数，应显示已提取数、已检查数和未核实数，并注明提取覆盖范围未知。不能用已提取数冒充原文总数。逐条检查也应区分“尝试查询”和“取得有效核查结果”。

## 5. 代码与复现讨论必须先确认归属

### 当前限制与风险

通用解析器会将包含 `github.com` 的链接标记为代码链接。但该链接可能指向被引用的方法、工具库或第三方实现，不能直接视为本文官方仓库。

即使仓库正确，一条“运行失败”的 issue 也可能只是环境安装问题；一条“结果不一致”的讨论可能已有作者解释或修复。仅根据标题、关键词或 issue 是否关闭来判断，容易误报。

### 提前处理

- 优先跟随论文、附录及明确关联的官方项目页面中的链接，并记录关联依据。
- 区分作者仓库、第三方实现和被引用工具；关联不明确时保留为待核实。
- 阅读相关讨论正文和关键回复，保留与论文结果的关系、作者说明、后续状态和核查时间。
- “未找到相关讨论”“第三方报告复现失败”“第三方报告复现成功”分别表达。本轮不运行代码，不生成系统亲自复现的结论。
- 如果查询只覆盖部分页面或时间范围，应明确标注，不能声称搜遍全部讨论。

验证时至少检查一个明确对应论文的仓库及其真实讨论，并检查一个容易误关联的链接。不要只使用标题与论文完全一致的简单案例。

## 6. 外部查询会改变耗时和失败处理方式

### 难在哪里

一篇论文可能需要查询几十条参考文献，再读取仓库、issue 和评论分页。外部限流、超时及模型重试会叠加。当前分析主流程以模型分析、校验和报告汇总为核心，新功能需要增加三类检查各自的进度与失败状态。

依据：[现有分析流程](https://github.com/kanekogaido/cs2-capstone--backend/blob/r2c-sync-2026-10-01/app/pipeline/orchestrator.py)。

### 最小必要处理

- 三项检查分别记录状态和结果；某项失败时保留其他已完成结果。
- 设置超时、有限并发、有上限的重试，以及服务限流后的等待策略。
- 缓存查询结果，保存来源和获取时间；论文解析结果按论文版本或文件摘要复用，避免版本混用。
- 前端展示实际阶段和部分结果，明确尚未完成的范围；部分检查失败时是否允许生成总评，由报告规则决定。
- 实测单篇论文耗时、请求量及模型费用，再确定等待提示和运行预算。

截至本次查阅，GitHub 未认证 REST 请求通常限每小时 60 次，普通用户认证请求通常为每小时 5,000 次，搜索端点还有更严格限制。应提前验证后端认证和实际可用额度。参考：[GitHub 限流说明](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)。

Crossref 官方建议缓存结果，并在收到限流响应时退避。参考：[Crossref 接口使用建议](https://www.crossref.org/documentation/retrieve-metadata/rest-api/tips-for-using-the-crossref-rest-api/)。具体配额应以实施时文档及响应信息为准。

## 7. 新报告、评分和评测需要一起设计

### 当前已确认的集成限制

现有后端报告固定为五个维度，创建任务请求仍要求 `venue_id`。新可信度报告需要独立结构和模式分流；旧五维合同继续用于旧功能，不能只修改页面标题或替换分数含义。

依据：[现有报告结构](https://github.com/kanekogaido/cs2-capstone--backend/blob/r2c-sync-2026-10-01/app/schemas/report.py)、[创建任务请求](https://github.com/kanekogaido/cs2-capstone--backend/blob/r2c-sync-2026-10-01/app/schemas/requests.py)。

### 最容易出错的规则

“不适用”和“检查失败”必须分开。理论论文可能不需要可运行代码，可以按确认后的规则排除这一维；GitHub 超时则表示该项检查未完成，不能同样排除后生成看似完整的高分。

已有[新合同 v0.1 评审稿](../../01_统一规范/可信度核查报告字段合同_v0.1.md)；联调前仍需确认并验证以下约定：

- 每项检查的完成状态、适用性、核查发现和证据来源。
- 空值、未核实、技术失败与风险结论之间的区别。
- 哪些条件下允许生成分项分数和总评，哪些条件下必须保留无法评估状态。
- 评分规则、模型、解析器、论文和报告结构的版本，以及外部核查时间。
- 总分由后端按确认规则计算；模型提供有证据的判断，不自行决定总分。

沿用当前产品基线：低分项需醒目提示，但不设置单项一票否决或总评级上限。本文不另外指定权重、阈值或分值区间。

### 评测不能只看输出是否完整

开发样本用于调整规则和提示词；另留一部分人工核查案例用于最终验收。人工判断应先于查看模型输出，关键争议由两人复核。

小样本阶段先记录具体误报、漏报、证据错误和覆盖缺口，不据此宣称整体准确率。对相同输入的重复运行，也应观察判断是否稳定、变化是否可解释。系统能生成报告与判断效果达到目标，分别登记。

## 8. 建议优先验证的内容

| 验证项 | 应取得的验证结果 |
|---|---|
| 解析与引用 | 几篇论文的人工引用总数、提取数、逐条匹配结果及失败原因；涉及表格时记录内容是否可用 |
| 主张核查 | 少量人工确定的核心主张，逐条展示系统判断、两端证据、条件和错误归因 |
| 仓库与讨论 | 仓库关联依据，一条带上下文和回复的真实讨论，以及无关链接的排除记录 |
| 新旧流程兼容 | 独立报告合同 v0.1 的评审与状态样例验证；正常、未核实、不适用及部分失败的展示样例；旧功能回归记录 |

建议先选 3–5 篇有不同版式和核查状态的论文作为共同开发样本。该数量仅用于启动验证，不足以代表整体效果。

先确认样本和人工预期，分别验证各条检查链路，再根据真实结果判断哪些可以进入开发、哪些需要补数据或调整实现。引用提取和主张证据仍不可靠时，应先修复或明确支持范围，再扩大开发。

字段联调可以使用明确标注的示例响应；技术可行性结论必须依据真实解析和查询结果。示例页面完成不能替代真实检查验证。

## 9. 验证记录模板

每项验证至少保留以下信息，并链接到对应 R2C 任务：

| 字段 | 填写内容 |
|---|---|
| 关联任务 | 对应 R2C 任务编号或链接 |
| 输入 | 论文标识、版本或文件摘要；相关仓库／讨论链接 |
| 环境与版本 | 解析器、模型、提示词、规则及代码版本 |
| 人工预期 | 应查出的结果、原文位置、来源和理由 |
| 实际输出 | 系统状态、判断、证据及可查看的结果位置 |
| 时间与消耗 | 运行时间、请求量、重试、模型消耗或费用 |
| 差异 | 提取遗漏、匹配错误、判断错误、失败状态错误等 |
| 后续处理 | 待解决的技术问题、调整方法和复测结果 |

目前本文所列验证均未登记为完成。验证后应将结果写入对应记录，并更新交付任务清单。
