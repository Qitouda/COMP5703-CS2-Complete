## 3. 阻塞项与复现证据

### A1 — 前后端尚未连接，不能以演示页面代替真实闭环（P0）

`frontend/src/App.tsx:14` 把 `mockAssessmentApi` 传给业务 hook，选项也直接读取 mock。`src/api/assessmentApi.ts` 只有接口声明。构建为生产版本也不会自动切换到真实后端。

前端草案 `/api/options` 与后端 `/v1/venues`、`/v1/models` 不同；前端输入采用 `source_type` 等内部字段，后端需要嵌套 `source`；后端 PDF 是先上传拿 upload_id 再创建任务。需要明确适配。路径不同本身不是合同违规，但没有适配就不能联调。重试可补端点，也可明确为创建新任务，不必强制某一种技术实现。

### A2 — 后端输入没有进入真实论文处理（P0）

`backend/app/api/routes_assessments.py:27` 只检查文件名后缀，返回 ID，没有读取或保存上传内容。`app/parsing/grobid.py:76` 与 `:79` 两个真实解析入口均直接抛 NotImplementedError；默认 StubParser 返回假文档。编排还把 upload_id 当解析路径传入，没有 upload_id→私有文件的解析。

实测：空文件和普通文本改名 test.pdf 均返回 HTTP 201；非法 arXiv ID 与不存在的 upload_id 均可创建任务并最终 completed、总分 7.2。提交不存在的 venue/model ID 也未被拒绝。上述都是默认演示模式结果，不能当真实论文分析。

### A3 — 完成响应缺字段，直接对接会导致前端报告页报错（P0）

`routes_assessments.py:50` 初始化的快照只有六个字段；完成后编排也未补 `source`、`venue`、`model`。实测用后端自己的 `Assessment.model_validate()` 校验完成响应，三字段均 missing。

前端 `AssessmentReport.tsx:78` 直接访问 `assessment.venue.name`，下一行访问 model。现有单测只检查 completed、进度和总分，没有检查完整响应。建议查询接口用完整 Assessment 响应模型；创建接口可返回轻量 receipt，但前端必须明确转换或立即查询，不能把 receipt 当完整 Assessment。

### A4 — 找不到的引文仍然通过评分校验（P0，质量门）

`app/validation/evidence.py:97` 对原文找不到的 quote 只降低证据位置置信度；`degradation.py:48` 仅在 evidence_links 为空时降低维度，未处理“链接存在但证据不可靠”。

实测把示例报告全部五条证据改成明确不在 paper_001 原文中的引文，再传入真实 source_index：校验返回 ok=true，五维仍为 8/7/7/8/6，其中两维置信度仍 high，总分 7.2，is_provisional=false。虽然有 warning，但缺乏可靠证据仍给出这些判断，不能满足质量验收。修复应将匹配失败标记为不可靠证据，影响依赖它的具体判断；必要时去分数、降判断置信度、说明不确定性。还应覆盖“引文存在于全文却不在所引用 chunk/page”的定位错误。

### A5 — 解析脚本把人工检查结果写成固定输出（P0，验收证据可信性）

`data/scripts/parse_pdf_pilot.py:190` 写死 paper_001 的来源 URL；`:197` 无条件写 parse_quality=good；`:211` 写 acceptance_gate=passed；`:216` 把所有页记为 visual_pages_reviewed；`:218` 固定写“18 页已人工检查”。脚本本身不执行人工查看或接收人工签署。这不能证明原作者没有检查过，但自动生成的文字不能证明检查发生，也不能用于后续样本验收。

要求自动检查和人工复核分开记录：自动运行默认 pending_review，真正人工检查单独记录 reviewer、时间、具体页码、发现问题和结论；来源参数化，空文本/扫描件/读取失败有明确质量状态。

### A6 — 质量基准和效果对比缺交付（P0，关闭第一轮的门槛）

`data/manifests/papers.csv` 三篇中仅一篇 parsed，其余 selected。仅有 `annotations/ai_trial/paper_001.json`，没有两人交叉试評与裁决结果，没有不同后端方案对比。单篇 AI 试跑是有效的流程探索，但不能同时证明 DP-04、DP-05、BE-04 完成。

3–5 篇是本轮要求；MVP 中的 30–50 篇是后续目标验证集，不应作为本轮额外阻塞。公开 PDF 不进入 Git 本身不是缺陷，只需精确来源/版本/哈希和可重现获取方式。

## 4. 应随下一轮处理的其他问题

- 前端 `useAssessment.ts:14` 单次 setTimeout 轮询失败只更新 requestError，不改变 effect 依赖，因此不会继续查询；processing 分支又未展示 requestError。会出现用户一直看到处理中且无恢复提示。补网络故障测试。
- FE-03 未展示 `claimed_contributions`；claim checks 不必覆盖每一项贡献，不能认为两个字段等价。
- 后端模型选项仅凭 API key 非空和 provider 配置便标为 available，没有最小调用验证状态；任务里的 model_id/venue_id 未用于合法性校验或选择。需要真实验证记录和一致路由。
- 后端真实数据 loader 已可读现有解析，但直接读 paper_001 返回 title=null、authors=[]、abstract=null；需将 source snapshot/manifest 中已有元数据合并进去或实现可靠提取，不能把缺作者容错理解为无需提取元数据。
- 数据标注 schema_version=0.1、dimension_assessments 等是数据库内部表示，不自动构成 API v0.4 违规；但缺显式转换和可供前端使用的完整 v0.4 报告，应由后端/数据组明确映射归属。
- 日志只在初次调用和修复返回后写 RunRecord；异常提前退出会漏掉该记录，attempts 默认 1，修复 token/时延未汇总。补失败、重试、修复三个路径的追踪证据。
- 任务保存在内存，重启丢失；数据库模型存在不代表任务已持久化。Docker compose 的 worker 指向不存在的 `app.pipeline.celery_app`。不要求一定采用 Celery，但不能把这份 compose 宣称为已验证部署方案；可以先交可运行的单进程 MVP 部署和真实限制。
- 交付任务清单仍有大量 Not Started，团队总览仍写待分配，仓库代码中有具体成员 TODO；应同步为经检查的当前状态，保存负责人、提交号、验收人和证据，避免用陈旧状态表代替实际审计。
