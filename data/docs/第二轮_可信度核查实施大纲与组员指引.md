# 第二轮：论文可信度核查实施大纲与组员指引

> 文档用途：供数据组、后端组和前端组共同讨论、开发与验收第二轮 **Paper Credibility Check**。
> 编写依据：`00_先读_第二轮文档说明.md`、`第二轮_可信度核查开发计划.md`、`MVP产品基线.md`，以及第一轮现有 50 篇论文结构化数据库。
> 当前状态：实施建议稿。新可信度 Rubric v0.1、报告字段合同 v0.1、分值、权重和类别阈值仍须取得正式版本并经真实样本校准后确认。
> 重要原则：第二轮新增可信度核查，不替换、不修改、不混算第一轮五维论文质量评分。

---

## 1. 项目变化概述

### 1.1 第一轮解决的问题

第一轮已经形成一套论文质量评分基础库，回答：

> 这篇论文从研究价值、证据、原创性、表达和可复现信息披露来看，整体质量如何？

第一轮五个维度为：

1. `research_value`：研究价值；
2. `soundness_evidence`：可靠性与论文内部证据；
3. `originality_positioning`：原创性与相关工作定位；
4. `clarity_usability`：清晰度与可用性；
5. `reproducibility_transparency`：可复现性信息与透明度。

现有交付包括：

- 50 篇锁定版本的机器学习论文；
- 论文来源、版本、PDF SHA-256 和页数；
- 章节、正文块、图表、定理、链接和语义描述；
- 50 份五维 AI 参考评分；
- 250 条维度评分；
- PostgreSQL 建表脚本和完整种子数据；
- 后端处理新论文时可复用的结构化程序。

### 1.2 第二轮新增的问题

第二轮新增独立的 **Paper Credibility Check**，回答：

> 论文的关键主张、文末引用和代码/外部复现材料中，是否存在需要读者进一步核查的风险？

首批三个维度为：

1. `claim_evidence_consistency`：主张与证据一致性；
2. `reference_verification`：参考文献存在性与元数据核查；
3. `code_reproduction_signals`：代码公开情况与外部复现线索。

### 1.3 最终应输出两份独立报告

同一篇论文可以同时具有：

```text
论文质量评分：8.2 / 10
可信度核查评分：6.5 / 10
可信度类别：Some concerns
```

两份报告含义不同，不允许将五维与三维相加成“八维总分”。

| 报告 | 回答的问题 | 数据来源 | 是否混算 |
|---|---|---|---|
| 第一轮五维质量评分 | 论文整体质量如何 | 论文内部结构化证据 | 否 |
| 第二轮三维可信度核查 | 哪些主张、引用、复现材料需要核查 | 论文内部证据 + 外部公开来源 | 否 |

一篇论文质量很高，仍可能有一条摘要主张外推过度；一篇质量一般的论文，也不一定存在虚假引用或可疑复现问题。

## 2. 第一轮现有数据结构

第二轮不推翻第一轮数据库。第一轮的论文身份、版本、章节、正文块和图表是第二轮的基础层。

### 2.1 论文与版本表

| 现有表 | 用途 | 第二轮处理方式 |
|---|---|---|
| `papers` | 稳定论文身份、标题、作者、摘要、venue、年份 | 直接复用 |
| `paper_versions` | 锁定 PDF 版本、来源 URL、哈希、页数、解析质量 | 直接复用；所有可信度结果必须绑定具体版本 |
| `benchmark_memberships` | 50 篇数据集划分、质量分层及发布状态 | 保留给第一轮；第二轮另建案例集成员表 |
| `dataset_releases` | 第一轮数据集发布版本 | 保留；第二轮单独登记可信度数据集版本 |

### 2.2 论文结构化表

| 现有表 | 用途 | 第二轮处理方式 |
|---|---|---|
| `paper_sections` | 章节层级、顺序和页码 | 复用，用于限定摘要、引言、References 和附录范围 |
| `paper_text_chunks` | 按章节切分的正文、页码和顺序 | 复用，用作主张和论文内部证据定位 |
| `paper_elements` | 图、表、公式、定理及页码 | 复用，用作实验结果与图表证据 |
| `paper_links` | 正文中的代码、数据、项目和其他 URL | 复用并扩展来源类型；不能只靠它判断官方代码 |
| `paper_semantic_descriptors` | 问题、贡献、主张、方法、评测、可靠性和局限等语义描述 | 可作为候选提取线索，但不能直接作为第二轮人工真值 |
| `paper_element_assets` | 图表对应 PDF、页码和按需图片位置视图 | 复用，支持前端回查表格和图片证据 |

### 2.3 第一轮评分和证据表

| 现有表 | 用途 | 第二轮处理方式 |
|---|---|---|
| `rubric_versions` | 登记评分规则版本 | 可复用版本管理机制，但要登记新的 credibility Rubric ID |
| `model_runs` | 模型、Prompt、运行时间和原始输出哈希 | 可复用运行审计机制 |
| `assessments` | 第一轮总体评分 | 不把第二轮结果直接塞入此表；建议另建可信度报告主表 |
| `dimension_assessments` | 第一轮固定五维分数 | 保留；其 `dimension_id` 仅允许旧五维，不应加入新三维 |
| `evidence_references` | 第一轮论文内部证据位置 | 证据定位思想可复用；第二轮还需要外部证据表 |
| `assessment_evidence_links` | 旧维度与证据的关系 | 保留给旧评分 |
| `reproducibility_checks` | 代码、数据、种子、超参数、硬件和预处理披露情况 | 作为第二轮代码维度的论文内部线索，不等于代码实际可复现 |
| `claimed_contributions` | 论文声称的贡献 | 可作为关键主张候选，不可未经核对直接当 Gold |
| `claim_checks` | 第一轮较简单的主张检查 | 可参考，但第二轮需要更细的主张来源、实验条件、查找范围和状态语义 |

### 2.4 为什么不能直接改旧表

`dimension_assessments` 的维度枚举已经锁定为五维，而且第一轮只使用论文内部证据。第二轮还涉及 Crossref 等文献元数据、官方代码仓库、GitHub issue、查询时间和技术失败。若把新结果塞入旧表，会产生以下问题：

- 新旧分数含义混乱；
- 无法表达外部查询失败和未核实；
- 无法保存 reference 逐条覆盖率；
- 无法保存仓库与论文的关联依据；
- 容易把“未找到”错误解释成“造假”；
- 后端和前端无法维护两条独立产品路径。

因此，第二轮应建立独立 Schema、SQL 表、报告文件和验证程序，只复用论文基础层。

## 3. 第二轮完整数据流

```text
用户输入 arXiv / PDF
        ↓
复用第一轮 PDF 锁定与结构化
        ↓
papers / paper_versions / sections / chunks / elements / links
        ↓
┌───────────────────────────────────────────────────────┐
│ 可信度核查                                            │
│ 1. 摘要/引言关键主张 → 后文证据对照                  │
│ 2. References 逐条提取 → 外部元数据匹配              │
│ 3. 代码来源确认 → 官方仓库 → 公开复现 issue/评论      │
└───────────────────────────────────────────────────────┘
        ↓
逐条 Findings + 覆盖率 + 不确定性 + 技术状态
        ↓
三个适用维度的小分
        ↓
可信度总分、四档类别、低分提醒
        ↓
独立可信度报告（不混入旧五维报告）
```

## 4. 三个维度的处理规则

## 4.1 Claim–Evidence Consistency

### 目标

从摘要和引言中提取影响读者判断的关键、可核查主张，再检查论文后文是否提供相符证据。

### 应提取的主张

- 性能优越主张；
- SOTA 或优于特定基线的主张；
- 效率、成本、速度或资源主张；
- 泛化、鲁棒性、隐私或安全主张；
- 理论保证；
- 首次提出或首次解决的主张；
- 数据集或基准覆盖范围主张。

### 不应自动纳入的内容

- 一般背景陈述；
- 研究动机；
- 修辞性表达；
- 无法在论文内部核查的宏观观点；
- 与论文结果无直接关系的未来愿景。

### 处理步骤

1. 识别摘要和引言章节；
2. 提取候选关键主张；
3. 合并重复或同义主张；
4. 标记主张类型和重要性；
5. 在方法、实验、表格、附录和结论中检索证据；
6. 核对数据集、指标、基线、实验条件和数字是否一致；
7. 输出判断、理由、两端证据和实际查找范围。

### 建议状态

| 状态 | 含义 |
|---|---|
| `supported` | 后文证据充分支持 |
| `partially_supported` | 有证据，但范围、条件或强度比主张更窄 |
| `evidence_not_found` | 在记录的检查范围内未找到对应证据 |
| `contradicted` | 主张与论文后文存在明确冲突 |
| `unable_to_determine` | 解析或信息不足，无法判断 |

### 误报控制

- 不同数据集、指标、基线或实验条件下的数字差异不能直接标成冲突；
- `evidence_not_found` 必须记录实际查过的章节和范围；
- 理论主张要核对假设与结论范围；
- 系统不能虚构页码、表格或不存在的证据；
- 第一周单条主张纵向切片必须标记 `scope_complete=false`。

## 4.2 Reference Verification

### 目标

对全部“成功提取”的文末参考文献做存在性和基本元数据核查。本轮不阅读全文判断被引论文是否支持正文论点。

### 处理步骤

1. 定位 References/Bibliography 章节；
2. 将跨行、跨页文本拆成逐条引用；
3. 解析标题、作者、年份、DOI、arXiv ID；
4. 优先 DOI 精确匹配；
5. 再用标题、作者、年份组合进行候选匹配；
6. 保存匹配来源、候选、冲突字段和查询时间；
7. 汇总提取覆盖率和核查覆盖率。

### 建议状态

| 状态 | 含义 |
|---|---|
| `matched` | 找到高度匹配的公开元数据 |
| `metadata_conflict` | 找到候选，但标题、作者、年份或 DOI 存在明显冲突 |
| `unverified` | 完成查询但没有足够信息确认 |
| `parse_failed` | PDF 条目没有被可靠拆分或解析 |
| `not_checked` | 尚未进入外部核查 |
| `query_failed` | 外部服务失败或限流 |

### 必须展示的覆盖率

```text
文末预计条目数
成功提取数
成功解析数
实际查询数
匹配成功数
元数据冲突数
未核实数
解析失败数
```

### 误报控制

- 搜不到不等于引用虚假；
- API 失败不等于引用有问题；
- 解析失败不得假装已经检查；
- 多个候选时保留候选及冲突理由，不强行选择；
- 每条外部结果必须保存来源和获取时间。

## 4.3 Code & Reproduction Signals

### 目标

检查公开代码是否存在、仓库是否确实与论文相关，以及公开仓库中是否存在与论文结果相关的复现讨论。本轮不运行代码。

### 来源范围

1. 论文正文、脚注和附录；
2. 补充材料；
3. arXiv/OpenReview 页面；
4. 论文项目主页；
5. 作者明确关联的 GitHub/GitLab 仓库；
6. 已确认仓库中的公开 issue 和评论。

### 仓库关联依据

至少应有一项强关联：

- 论文直接给出仓库链接；
- arXiv/OpenReview/项目主页链接到仓库；
- 作者主页链接到仓库；
- README 明确写出论文标题、作者和引用信息。

名称相似不是充分依据。

### 建议状态

| 状态 | 含义 |
|---|---|
| `official_code_available` | 找到可访问且关联明确的代码 |
| `independent_success_report` | 有可信第三方公开报告成功复现 |
| `failure_or_data_problem_report` | 有公开失败或数据问题报告 |
| `discussion_inconclusive` | 有相关讨论，但无法判断 |
| `no_relevant_public_feedback` | 检查了确认仓库，未发现相关反馈 |
| `repository_not_confirmed` | 找到候选仓库，但关联依据不足 |
| `no_public_code_found` | 在已列明来源中未找到可访问代码 |
| `query_failed` | 外部服务失败 |
| `not_applicable` | 理论等不依赖运行代码的论文 |

### 误报控制

- “没有评论”不等于成功复现；
- “没有公开代码”不等于欺诈；
- 第三方 issue 是外部线索，不是系统实证；
- 作者回复、issue 关闭、修复提交需要一起记录；
- 代码公开可以提高透明度，但第一版本不运行代码，因此不能授予代表亲自复现认证的满分。

## 6. 建议新增的数据库表

以下是建议逻辑模型，最终字段名须与正式字段合同 v0.1 对齐。

## 6.1 `credibility_assessments`

一份可信度报告的主记录。

| 字段 | 建议类型 | 说明 |
|---|---|---|
| `credibility_assessment_id` | TEXT PK | 报告 ID |
| `paper_version_id` | TEXT FK | 必须绑定具体 PDF 版本 |
| `rubric_id` / `rubric_version` | TEXT | 新可信度 Rubric 版本 |
| `model_run_id` | TEXT NULL FK | 自动报告对应模型运行 |
| `assessment_source` | TEXT | `ai`、`human`、`adjudicated` |
| `status` | TEXT | `draft`、`reviewed`、`approved`、`unable_to_assess` |
| `scope_complete` | BOOLEAN | 是否完成约定范围 |
| `overall_score` | NUMERIC NULL | 适用维度全部可评分时才有值 |
| `overall_category` | TEXT NULL | 四档风险类别 |
| `summary` | TEXT | 总体判断及边界 |
| `limitations` | JSONB | 检查局限 |
| `created_at` / `completed_at` | TIMESTAMPTZ | 时间 |

## 6.2 `credibility_dimension_scores`

三维分项评分。

| 字段 | 说明 |
|---|---|
| `dimension_score_id` | 主键 |
| `credibility_assessment_id` | 所属报告 |
| `dimension_id` | 三个固定维度之一 |
| `applicability` | `applicable`、`not_applicable`、`unable_to_assess` |
| `score` | 可为空 |
| `weight` | 经正式 Rubric 确认的权重 |
| `summary` | 维度说明 |
| `coverage` | 已检查范围及覆盖率 JSON |
| `confidence` | 置信度 |
| `failure_reason` | 无法评分时的原因 |

不得把 `unable_to_assess` 写成 0 分。

## 6.3 `credibility_claims`

摘要/引言关键主张。

| 字段 | 说明 |
|---|---|
| `credibility_claim_id` | 主键 |
| `paper_version_id` | 论文版本 |
| `source_chunk_id` | 主张所在正文块 |
| `claim_text` | 原文 |
| `claim_type` | 性能、效率、泛化、理论、原创性等 |
| `importance` | 关键程度 |
| `verifiability` | 是否可通过论文后文核查 |
| `dedup_group_id` | 同义/重复主张组 |
| `page_number` | 页码 |
| `extraction_source` | 人工或模型 |
| `review_status` | 候选、已复核、排除 |
| `exclusion_reason` | 排除理由 |

## 6.4 `claim_evidence_checks`

逐条主张核查。

| 字段 | 说明 |
|---|---|
| `claim_check_id` | 主键 |
| `credibility_claim_id` | 被核查主张 |
| `verdict` | 五种状态之一 |
| `reasoning` | 判断理由 |
| `dataset_context` | 对应数据集 |
| `metric_context` | 对应指标 |
| `baseline_context` | 对应基线 |
| `condition_context` | 其他实验条件 |
| `searched_scope` | 已查章节/页码范围 |
| `scope_complete` | 是否完成约定范围 |
| `review_status` | 人工复核状态 |

一个主张可以连接多个论文内部证据。

## 6.5 `credibility_internal_evidence`

主张核查使用的论文内部证据。

| 字段 | 说明 |
|---|---|
| `internal_evidence_id` | 主键 |
| `claim_check_id` | 所属核查 |
| `chunk_id` / `element_id` | 正文块或图表，至少一个存在 |
| `evidence_role` | `supports`、`limits`、`contradicts`、`context` |
| `excerpt` | 短摘录 |
| `page_number` | 物理 PDF 页码 |
| `location_confidence` | 位置可靠性 |

## 6.6 `paper_references`

逐条文末参考文献。

| 字段 | 说明 |
|---|---|
| `paper_reference_id` | 主键 |
| `paper_version_id` | 论文版本 |
| `sequence_index` | 文末顺序 |
| `raw_reference_text` | 原始完整条目 |
| `parsed_title` | 解析标题 |
| `parsed_authors` | 作者 JSON |
| `parsed_year` | 年份 |
| `parsed_doi` | DOI |
| `parsed_arxiv_id` | arXiv ID |
| `page_start` / `page_end` | 页码 |
| `parse_status` | 成功、部分、失败 |
| `parse_confidence` | 解析置信度 |

## 6.7 `reference_verification_checks`

外部元数据核查。

| 字段 | 说明 |
|---|---|
| `reference_check_id` | 主键 |
| `paper_reference_id` | 文末引用 |
| `status` | 匹配、冲突、未核实、查询失败等 |
| `provider` | Crossref、OpenAlex、arXiv 等 |
| `query` | 实际查询条件 JSON |
| `matched_title` | 候选标题 |
| `matched_authors` | 候选作者 |
| `matched_year` | 候选年份 |
| `matched_doi` | 候选 DOI |
| `source_url` | 原始元数据页面/API URL |

## 7. 文件和数据库的关系

建议每篇可信度案例在 Git 中保留可审计 JSON，然后统一导出 SQL：

```text
data/credibility_cases/reviewed/paper_XXX/
├── case_metadata.json
├── claims.json
├── claim_checks.json
├── references.json
├── reference_checks.json
├── repositories.json
├── reproduction_signals.json
├── findings.json
└── assessment.json
```

对应关系：

| JSON | SQL 表 |
|---|---|
| `assessment.json` | `credibility_assessments`、`credibility_dimension_scores` |
| `claims.json` | `credibility_claims` |
| `claim_checks.json` | `claim_evidence_checks`、`credibility_internal_evidence` |
| `references.json` | `paper_references` |
| `reference_checks.json` | `reference_verification_checks` |
| `repositories.json` | `paper_code_repositories` |
| `reproduction_signals.json` | `reproduction_signals` |
| `findings.json` | `credibility_findings` |

Git 中的 JSON 是数据组审查和版本管理来源；SQL 是后端运行时交付。不得只修改 SQL 而没有源 JSON。

## 8. 数据组实施步骤

## 阶段 0：取得并冻结正式输入

在开发前取得：

- 可信度 Rubric v0.1；
- 可信度报告字段合同 v0.1；
- 技术难点与提前验证；
- 样本与复评记录；
- 验收路径；
- 任务主表；
- 决策记录；
- `r2c-sync-2026-10-01` 对应分支、PR 或标签。

当前本地仓库仅看到 `main`，尚未看到上述交接分支或标签。必须先确认远端是否需要 fetch，或让组员提供正确仓库/PR。正式合同未取得前，可以做带 `draft` 标记的试验，不能把建议字段宣称为最终接口。

### 阶段 0 交付

一份版本确认记录：

```text
代码基线：
旧五维 Rubric：
可信度 Rubric：
字段合同：
Schema 版本：
已确认规则：
待确认规则：
```

## 阶段 1：选择首批 6–10 篇人工案例

不要立即处理全部 50 篇。首批至少覆盖：

- 正常且证据充分；
- 主张部分支持；
- 后文未找到证据；
- 具体条件或数字冲突；
- reference 正常匹配；
- reference 元数据冲突或未核实；
- 有明确官方代码；
- 有成功/失败复现讨论；
- 无公开代码；
- 理论论文，代码维度不适用；
- 解析质量不足或外部查询失败。

案例来源可以是现有 50 篇，但旧五维分数、录取决定和 sample band 不能作为可信度真值。

## 阶段 2：制作第一篇主张纵向切片

第一周先完成一篇论文的一条人工核对发现：

```text
摘要/引言主张
→ 主张页码和 chunk_id
→ 后文证据页码和 chunk_id/element_id
→ 实验条件核对
→ 人工预期状态
→ 判断理由
→ scope_complete=false
→ 后端保存
→ 前端回查两端证据
```

这一阶段只证明链路真实可用，不代表整篇可信度核查完成。

## 阶段 3：完成首批主张人工标注

对摘要和引言的关键可验证主张进行：

1. 提取；
2. 去重；
3. 保留/排除判断；
4. 后文证据查找；
5. 条件和数字核对；
6. 状态及理由标注；
7. 遗漏复查。

正式 Gold 案例建议两人独立标注、记录分歧并仲裁。第一周试验可以单人，但必须标为候选或 reviewed，不能直接标 Gold。

## 阶段 4：建立 reference 人工测试集

先人工检查 20–30 条参考文献拆分和字段解析，再接外部 API。统计：

- 拆分正确率；
- 标题解析问题；
- 两条错误合并；
- 一条错误拆分；
- 跨页丢失；
- DOI/年份解析问题。

只有解析结果可用后，才评估匹配算法，否则外部匹配错误无法区分来自 PDF 解析还是元数据搜索。

## 阶段 5：建立仓库和复现线索人工案例

人工确认：

- 哪个仓库确实关联论文；
- 关联依据是什么；
- issue 是否真的讨论论文结果；
- 是否为第三方；
- 作者是否回复；
- 是否有修复；
- 哪些讨论与复现无关应排除。

## 阶段 6：用真实案例校准 Rubric

需要确认：

- 每个状态对应的分值；
- 三维权重；
- reference 覆盖率如何影响评分；
- 未核实是否扣分以及扣多少；
- 代码公开但无人复现的分值；
- 第三方成功/失败线索的影响；
- 理论论文适用性；
- 总分为空的条件；
- 四档类别阈值；
- 低分提醒阈值；
- 代码维度因不实际运行代码而设置的最高分边界。

文件已确认的原则：

- 主张维度采用去重后全部有效主张的最低分；
- 总体按适用维度汇总；
- 单项低分不封顶总评级；
- 低分和关键发现必须醒目提示；
- 任一适用维度无法评分时，总分和类别为空；
- 具体数值和类别阈值仍须校准确认。

## 阶段 7：复评后端输出

数据组对后端结果记录：

1. 重要风险漏报；
2. 正常样本误报；
3. 状态判断错误；
4. 证据定位错误；
5. 主张遗漏；
6. reference 错配；
7. 找错仓库；
8. 外部来源误读；
9. 覆盖率不真实；
10. 技术失败被错误当成安全。

分析交付完成与模型效果达标要分开记录。

## 阶段 8：小规模通过后扩展

推荐扩展顺序：

```text
1 篇纵向切片
→ 3 篇技术验证
→ 6–10 篇 Rubric 校准集
→ 15–20 篇可信度评测集
→ 再决定是否扩到现有 50 篇
```

## 11. 两周实施顺序

### 第一周前段：基线、合同与样本

- 确认代码分支/标签；
- 取得 Rubric 和字段合同；
- 确认新旧报告完全独立；
- 建立首批人工样本清单；
- 建立 JSON Schema 和 SQL 草案；
- 确定状态枚举和失败语义。

### 第一周后段：一篇论文纵向切片

- 人工提取一条摘要/引言关键主张；
- 找到后文证据；
- 保存两端位置；
- 后端生成真实 Finding；
- 前端回查证据；
- reference 和仓库连接器分别完成技术探测。

### 第二周前段：三维集成

- 完成首批全部关键主张；
- 全部成功提取的 references 有逐条状态；
- 确认代码仓库并读取相关公开讨论；
- 生成三个分项；
- 根据确认规则生成总分和类别；
- 异常、空值、不适用和失败路径进入同一报告。

### 第二周后段：复评和验收

- 正常、风险和争议样本对照；
- 统计漏报、误报、证据错误和覆盖率；
- 修复可复现问题并回归；
- 验证旧五维功能未被破坏；
- 固定数据、代码、Rubric、Schema 和报告版本；
- 记录剩余限制，不夸大效果。

## 12. 完成定义

第二轮只有在以下条件满足时才算完成：

### 数据和规则

- 三维含义及适用性已确认；
- Rubric 和字段合同版本已锁定；
- 有正常、风险、争议和技术失败人工案例；
- Gold、reviewed 和候选状态分开；
- 每个重要发现均可回查证据。

### 主张核查

- 摘要/引言关键主张范围有明确规则；
- 主张去重和遗漏复查有记录；
- 证据位置真实存在；
- 条件不同不会被误判为冲突；
- 未找到证据时保存查找范围。

### Reference 核查

- 全部成功提取条目都有逐条状态；
- 提取数、检查数和未核实数可统计；
- 查询失败与未匹配分开；
- 不将未核实自动判断为虚假。

### 代码与复现线索

- 仓库关联有依据；
- issue/评论来源及时间可查；
- 作者回复和修复状态一并呈现；
- 第三方线索不被描述为系统实证；
- 明确声明本轮没有运行代码。

### 产品和回归

- 用户能选择旧评分或可信度核查；
- 两套分数不混算；
- arXiv 和 PDF 有明确成功或失败结果；
- 空值和失败不会显示为 0 或“安全”；
- 原 50 篇数据库、旧 SQL 和五维报告继续通过验证。

---

## 13. 明确不做的事情

- 不运行论文代码或重新训练模型；
- 不验证论文实验数值是否能够被实际复现；
- 不判断作者主观动机；
- 不自动下“欺诈”或“学术不端”结论；
- 不把 venue 或录取结果当可信度证据；
- 不逐篇阅读全文验证引用是否支持正文论点；
- 不保证发现所有代码或网络讨论；
- 不把旧五维分数当作可信度标签；
- 不制作五维与三维的联合八维分数；
- 不因缺少外部讨论自动扣成复现失败。

## 14. 组员拿到本文档后首先要做什么

### 数据组

### 所有人共同确认

第一项真正的集成验收不是“得到一个可信度总分”，而是：

> 同一篇真实机器学习论文的一条摘要/引言关键主张，能够连接到后文证据，产生一条人工确认的判断，并在前端回查主张端与证据端；未完成的范围被明确标出。

完成这条纵向链路后，再扩展 references、代码仓库、评分汇总和更多论文。
