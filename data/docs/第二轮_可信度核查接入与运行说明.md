# 第二轮可信度核查：接入与运行说明

## 1. 本轮交付到什么程度

第二轮作为第一轮五维论文质量评分的**独立扩展**接入。第一轮表和已有分数不被覆盖；第二轮分别检查：

1. 论文关键主张与后文证据是否一致；
2. References 是否能正确拆分，并能否从外部元数据核实；
3. 官方代码仓库与公开复现讨论中是否存在可回查信号。

当前 Rubric 是 `0.1-draft`，权重和类别阈值尚未获组内批准。因此程序会生成核查状态、覆盖率、证据和失败原因，但不会编造正式分数。第二轮分数也不会和第一轮五维分数相加。

## 2. 与第一轮结构的连接

第一轮的权威结构仍是：

- `paper_versions`：锁定 PDF 版本、SHA-256 和页数；
- `paper_sections`：章节与页码范围；
- `paper_text_chunks`：可引用正文块；
- `paper_elements`：图、表、公式、定理及其页码；
- `assessments` / `dimension_assessments`：第一轮五维质量评分。

`scripts/build_credibility_case_from_parsed.py` 是连接器。它把现有 `data/parsed/<paper>/<version>/` 中的 `metadata.json`、`sections.json`、`chunks.jsonl`、`elements.json` 映射到第二轮合同。它不会重新解析 PDF，也不会调用 AI。

第二轮 SQL 使用独立的 `credibility_r2` schema。`paper_version_id`、`chunk_id`、`element_id` 都通过外键关联第一轮表，因此后端无法导入指向不存在正文或图表的可信度证据。

## 3. 真实纵向案例

已提供 `paper_001` 的一条真实、可回查证据链：

- 主张端：摘要，第 1 页，`paper_001_v3_chunk_0001`；
- 证据端：实验结果，第 7 页，`paper_001_v3_chunk_0015`；
- 判断：该条性能主张得到后文定量结果支持；
- 边界：只检查一个主张，所以 `scope_complete=false`、`claim_scope_complete=false`，不是全文可信度结论。

文件位置：

- 人工增量标注：`data/credibility_cases/annotations/paper_001_one_claim.json`
- 合并后的完整案例：`data/credibility_cases/reviewed/paper_001_v3.json`
- JSON/HTML 报告：`data/credibility_reports/draft/`
- 可导入 SQL：`sql/031_credibility_seed_paper_001.sql`

## 4. 后端运行顺序

数据库导入：

```bash
psql -d <database> -f sql/001_initial_schema.sql
psql -d <database> -f sql/020_seed_all_structured_papers.sql
psql -d <database> -f sql/030_credibility_schema.sql
psql -d <database> -f sql/031_credibility_seed_paper_001.sql
```

生成案例与报告：

```bash
python3 scripts/build_credibility_case_from_parsed.py \
  --paper-id paper_001 --version v3 \
  --annotation data/credibility_cases/annotations/paper_001_one_claim.json \
  --output data/credibility_cases/reviewed/paper_001_v3.json

python3 -m credibility_r2 build-report \
  data/credibility_cases/reviewed/paper_001_v3.json \
  --output data/credibility_reports/draft/paper_001_v3.report.json \
  --html data/credibility_reports/draft/paper_001_v3.report.html
```

离线校验与测试：

```bash
python3 -m unittest discover -s tests -p 'test_credibility*.py'
python3 -m credibility_r2 validate data/credibility_cases/reviewed/paper_001_v3.json
make validate
```

## 5. API Key 与职责边界

导入 SQL、读取结构、生成离线报告、校验证据位置均不需要 API Key。只有显式使用 `--online` 查询 Crossref 或 GitHub 公共接口时才会访问网络；这不是后端导入的前置条件。

后端可以使用自己的模型和提示词完成新论文的核查，但输出必须满足 `schemas/credibility_case.schema.json`，并通过 `credibility_r2` 的位置与状态校验。数据组交付的是合同、基准案例、Rubric 草案和已核查记录，不替后端托管模型密钥。

## 6. 批量扩展前仍需确认

在对全部论文执行第二轮之前，组内仍需冻结正式 Rubric：三维权重、状态到分数的映射、低分阈值和四类结果边界。未冻结前，程序正确行为是保留 `score=null`，而不是用临时数字冒充正式结果。
